## 0 阅读指南

### 0.1 范围、目标读者与推荐阅读路径

**这套系统是什么。** 给定一个研究总目标，meta-research 自己出题、自己设计验证、自己执行评估、自己判断是否迭代，长程数百轮无人值守地推进，且不偏离目标、不积累矛盾，最终留下一份**任何结论都能回溯到一次具体测量（及其关联的训练 / 评估轨迹）**的可复查证据资产。它的「元能力」在于：把"如何做研究"这件事本身——出题、复用判断、对照设计、收口下结论——固化成确定性的流程与不变量，而把"具体研究内容"交给可替换的智能运行时。具体研究内容是可换的，元能力是稳定的。

**本部分范围。** 只讲**系统架构设计**（核心概念 / 对象 / 契约 / 流程 / 机制 / 数据）；实现技术细节（skill / MCP / 编排器 / 文件夹）见《第二部分》，里程碑与验收见《第三部分》。

**推荐阅读路径。** 先读 **§1（核心设计思想：定位 / 六原则 / 两根支柱 / 契约）**——这是做系统时最先、最重要定义出来的根基；再读 **§2（四层架构 + 元循环鸟瞰）** 看系统怎么动；**§3（四阶段执行流程 + 跨阶段功能）** 顺时间线读一轮怎么跑；**§4（正确性与运行机制）** 看怎么保证不漂移、可恢复、可追溯；**§5（数据与持久化）** 落到 DB + 文件双底座。**DDL 全文在附录 A**（正文 §5 只给摘要 + 约束映射 + 索引）。

## 1 边界、对象与契约

> 本章定义系统**最核心、最先确定**的东西：是什么、操作哪些对象、哪些约束永远成立。**对象只在 §1.2/§1.3 定义、不变量只在 §1.4 定义**，全文别处只引用。四层架构（怎么分层）见 §2.1。

### 1.1 系统定位、边界与设计原则

**1.1.1 系统输出 = 问题树 + baseline 池 + 决策账本。** meta-research 是长时自主研究系统：输入一个研究总目标（goal），输出**三样核心资产**——① 一棵**问题树**（记录"问过什么、怎么验证、得到什么结论"的研究状态）；② 一座 **baseline 池**（积累可复用方法与可复查测量的研究资产与证据）；③ 一本**决策账**（逐轮可审计的 DECISION / LEDGER）。**问题树 + baseline 池是系统的两根支柱**（§1.2 同等展开），决策账记录过程"为什么这么走"。

**1.1.2 输入、外部依赖与非目标。** 输入 = goal（+ 人类 directive）。外部依赖 = 可替换智能运行时（Codex）、文献 / 代码检索（只读）、外部开源 baseline（经 import 准入 §3.6）。**非目标**：不替人跑某一个固定实验、不承诺具体研究产出、不在会话里持状态（状态只在库）。**更名（原 Auto-Research）的用意**：价值不在替人跑某个实验，而在把研究的**元能力**——出题与排序、复用与对照判断、证据强制与收口、长程不漂移——做成**可重放、可审计、可长跑**的机制。

**1.1.3 概念层 vs 物理资产层（DB + 文件双底座 / 双管理）。** **结构化状态的唯一真相在 SQLite（P1）**——系统"现在处于什么状态"只有一个查询入口；**文件系统管非结构化内容**（代码 / checkpoint / log / md），**由 DB 的 `path + hash + metadata` 索引与校验**（文件是 Codex↔DB 的双向中介、大资产只引用不复制）。即：**状态真相单一（DB），存储底座双管理（DB + 文件）**——双底座不冲突 P1。本章在**概念层**定义对象与契约；**物理落地**（DB schema + 文件布局 + 缝合）见 §5。

**1.1.4 六项设计原则 P1–P6。**
- **P1 真相只在一处**：系统"现在处于什么状态"永远只有一个查询入口（SQLite）。md 文档是渲染视图，不是真相。
- **P2 机制与策略分离**：循环机制代码不含任何可调数值（**旋钮 = 影响研究语义 / 门禁 / 预算 / 选择的数值**；SQLite `busy_timeout`、队列轮询间隔等纯工程常量不在此列）；所有旋钮集中在 `policies/policy.yaml`（全量见附录 C）。
- **P3 智能与确定性分工**：编排器是确定性程序、从不推理；Codex 会话是无状态工人、从不持有状态。
- **P4 失败即观测**：任何失败（含工程失败）如实入账、不自行兜底，裁决权属下一轮 reasoning。
- **P5 人不直接改库**：一切人类介入经 DIRECTIVE 收件箱，由门禁在指定时机消费。
- **P6 阶段边界即检查点**：步进函数幂等，任意时刻 kill -9 重启可续跑。

> **与 DeepScientist 的四点根本差异**（由上述原则而来）：① 确定性编排器自动推进 ＞ anchor 不自动推进；② SQLite 单一真相 + 门禁写入 ＞ 文件散落状态；③ 编译器按阶段分区预算检索 ＞ 无精细上下文管理；④ 流程层确定、智能层无状态 ＞ prompt/skill 主导全程。

### 1.2 研究资产域模型：两根支柱 + 一套账本

> 全文枢纽：决定问题树如何记录研究状态、池里的东西如何被**识别 / 对照 / 复用**。**对象语义只在本节与 §1.3 定义**；字段级落库见 §5。

**1.2.1 问题树：研究状态的主结构。** 问题树承载研究"现在走到哪、答没答"。树侧域模型：

```
goal
 └─ question (parent ⇄ child 自引用成树)
      ├─ idea          候选想法（含 wildidea 映射与 6 维评分）
      ├─ question_dep  依赖边：→问题 / →baseline（调度前置）
      └─ answer ─→ evidence   仅 answered/refuted 产 answer；answer 绑 ≥1 条 evidence
```

- **question 节点 = 一个待答研究问题**；身份 = 问题语义本身（非某个 .py）；`status ∈ {open, active, answered, refuted, inconclusive, dead_end}`（**终态 = {answered, refuted, dead_end}（`trg_q_no_reopen` 冻结不可重开）；`inconclusive` 非终态、与 open 一样可被重调度；完整迁移、重访与依赖调度可见性见 §4.2**）。
- **角色分层（准入 → 关闭 → 派生）**：出题时按「研究者想问的问题」准入（`text` 即语义身份）；**攻坚前须收敛为可由证据关闭的命题**（I3 是唯一被机械强制的定义性角色；不可收敛的问题只能 decompose / 重述 / dead_end）；调度（status / score / est_cost / dep，§4.2）与展示（问题卡，§4.5.2）是同一对象上的派生角色。**每一层问题都可证据关闭**：叶子经 evaluation、内部节点经 child_answer 聚合、特殊问题经 literature / human（§3.5.2 证据多态）。**立题下界（软约束；执行点 = reasoning 提示词，版本化，无门禁拦截）**：小于「一次可关闭的测量或复用判定」的事不立题——工程报错归 bundle 自愈（§3.4.2）、解释性叙述归 cycle_report / DECISION、名词 / 现状询问归 interaction（§4.6）；「值不值得 / 该不该」类调度判断记 DECISION、不立题。
- **score / est_cost 的唯一维护点（硬）**：由 reasoning 每次 R3 选题打分产出（`selection.scores[]`），经 `persist_selection` 同步写回 question 列（§3.5.3 / §4.2.4）；四元打分权重是 policy 旋钮（附录 C acquisition），公式实现形态见《第二部分》§6.4。
- **父子聚合**：`parent_id` 自引用成树；reasoning 分解（decompose）写子问题；**父问题靠子答案聚合关闭、价值回传**（机械路径：decompose 释放父问题并写子依赖 → 子答案 satisfied → 父问题聚合轮，见 §4.2.4 `add_children`）。
- **`question_dep` 依赖**：问题→问题（dep_type=question）/ 问题→baseline（dep_type=baseline）——前置未就绪不可调度（调度语义见 §4.2）。
- **`visit_count`**：访问 / 推进信号（四元打分 §3.5.3 / 防贪心用）。
- **证据关闭**：仅 answered/refuted 产 `answer`（绑 goal_ver），且必带 ≥1 条有效 `evidence`（**I3**，§1.4.3）；evidence 多态（evaluation / literature / child_answer / human）。

**1.2.2 baseline 池：研究资产与证据的主结构。** 池组织可复用资产、对照对象与证据。内部用**三个正交维度**建模——一个"被研究的东西"由三个互相独立的维度刻画：

```
结构（baseline）           —— 前向逻辑 / 算法结构
  × 训练任务设置（variant） —— 训练数据 / 流程 / 超参；纯规则模型则是阈值参数 → 产出 checkpoint(s)
  × 评估协议（evaluation）  —— 评估数据 / 分割 + 指标 → 测出指标值
```

**关键澄清：「协议」专指评估协议（evaluation 层）。** 变体层绑的是"训练任务设置"（落在 `variant.config_json`），它决定模型**长什么样、怎么训出来**；评估协议决定模型**在什么数据上、用什么指标被测量**。两者是两个不同的东西，**不要混为一谈**——这是对象模型最重要的一处厘清。

**层次**：

```
baseline                              # 前向逻辑（结构代码）
└── variant                           # 结构 + 训练任务设置（一次执行）
    ├── checkpoint(s)                 # 被评估对象，可多个（LOSO/SEED 15 折一次命令跑完）
    └── evaluation(s)                 # 对照元：变体 × 一个评估协议@版本（逻辑测量单元）
        └── attempt(s)                # 一次真实评估执行（重试/复现各一条；canonical 标基准）
            └── metric_result         # 各折(fold) + 聚合(aggregate)
```

**语义判据**（归属由 plan 按意图声明，编排器据此占坑/建对象）——三问决策树：

```
1. 前向计算逻辑变了吗？（结构种类 / 拓扑；不含改头数、MLP 层数、维度等规模参数）
   → 变：新 BASELINE
2. 模型需要重新训出来吗？（改训练设置 / 超参 / 数据，checkpoint 会变）
   → 变：新 VARIANT
3. 只改评估协议吗？（评估数据 / 指标，不动训练）
   → 是：同变体、新 EVALUATION（拿现有 checkpoint 重评，不重训）
```

判据是**语义事实**，对规范代码与烂代码、对训练模型与纯规则模型一致适用。标准判例：改注意力头数 / MLP 层数 / 隐藏维度 → 同 baseline 的新变体；加 top-5 指标 / 换评估集 → 同变体的新 evaluation；换结构（RNN→Transformer）→ 新 baseline；LOSO 15 折 → 一变体一次执行产 15 checkpoint、一 evaluation 内 15 fold + 1 aggregate。

**对照元 = evaluation**（变体 × 评估协议@版本）。一次**对照** = 同一评估协议下 ≥2 个 evaluation（来自不同变体、可跨 baseline）比同一指标。硬前提：同评估协议、选共同指标。三层粒度分工：baseline 定前向逻辑、variant 训出可用模型、evaluation 取最终指标值（用于对照下结论）。

**协议内部两部分可变性**：场景（scope_spec_json：评估数据 / 分割 / checkpoint 选择 / 流程）**不可变**（改即升 version，护 I1）；声明指标集（protocol_metric）**可追加**（不升版，I2 依据）。

**1.2.3 决策账本：过程轨迹与审计。** 账本记录"为什么这么走"，不抢支柱位置：**DECISION**（决策日志，actor ∈ agent/gate/judge/human/orchestrator，append-only）· **LEDGER**（预算台账：每 Runner 调用 / RUN 的 tokens / 时长 / wall-clock / 货币）· **CARD**（卡片：物化摘要，见 §1.3.4 / §4.5）。账本经 EVIDENCE 等关联树 / 池，本身 append-only。

**1.2.4 三者关系。** **问题树 = "研究走到哪"**（状态）· **baseline 池 = "有什么可用资产与证据"**（资产）· **决策账 = "为什么这么走"**（轨迹）。问题树与池**管理方式相互独立**，经两条边耦合：**结论语义耦合**经 EVIDENCE（某 evaluation 的指标作证据回答某问题）；**调度 / 前置耦合**经 `question_dep`（某问题依赖某 baseline 就绪）。除此两条，互不直接改写对方。

### 1.3 核心对象目录（对象定义唯一权威）

> 全系统对象按所属支柱分三侧；**对象语义只在此定义**，§2/§3/§4/§5 只引用并标角色（生长 / 管理 / 落库），定义回链本节。

- **1.3.1 树侧对象**：`question`（问题节点）· `question_dep`（问题依赖边：→问题 / →baseline）· `idea`（候选想法，含 wildidea 映射与 6 维评分）· `answer`（结论，绑 goal_ver）· `evidence`（多态证据，evaluation 类必指向 `metric_result`）· `goal` / `answer_applicability`。
- **1.3.2 池侧对象**：`baseline`（前向逻辑 / 结构）· `variant`（结构 + 训练设置，append-only）· `checkpoint`（可评 target，一变体可多个）· `evaluation`（对照元 = 变体 × 协议@版本）· `evaluation_attempt`（一次真实执行）· `metric_result`（fold / aggregate）· `protocol`（评估协议@版本）· `metric_def` / `protocol_metric`。
- **1.3.3 过程侧对象**：`cycle`（一轮）· `route`（本轮形态，7 形态见 §2.3）· `selection`（reasoning 选下一步，**不写 route**）· `build_target` / `run`（执行单元）· `directive`（人类指令）· `external_candidate` / `license_review` / `external_import`（import 准入，§3.6）· `interaction_message` / `interaction_classification` / `interaction_reply`（人机，§4.6）· `interaction_request`（文件请求单：系统向人请求供给，§4.6.8）。
- **1.3.4 卡片体系（指代物化）**：问题卡 / 子树摘要卡 / 方法族卡 / 基线卡 / 变体卡 / 失败卡 / 协议卡——**物化在 DB `card` 表**、定额 token、为上下文供给设计；生命周期与索引见 §4.5、字段见 §5.B。
- **1.3.5 对象引用规则**：树侧 / 池侧**只经 EVIDENCE（结论语义）+ `question_dep`（调度前置）两类边耦合**，其余直接耦合禁止；过程侧引用树 / 池但不被其引用；**不在别处重定义对象语义**。

### 1.4 架构契约：池管理高层概念（铁律）与细节不变量（定义 what）

> **永远不能破**的契约，定义在此唯一权威；§4 只讲门禁 / 状态机 / 审计**如何落实**（how-enforced，映射见 §1.5）。

>   · **下层 = 不变量 I1–I6 与 append-only**：门禁可机械校验的细节状态谓词（怎么强制），是上层概念的落点。

## 2 总体架构与元循环鸟瞰

> 本章给系统的**静态分层鸟瞰**（四层职责）+ **动态主线鸟瞰**（元循环一轮怎么走）。对象与契约见 §1、不在此重定义；每阶段细节见 §3、机制见 §4。

### 2.1 四层架构（一句话视图 + 职责边界）

系统分四层，自上而下是"可调—确定—真相—执行"：

| 层 | 落地物 | 职责 | 原则归属 |
|---|---|---|---|
| **策略层** | `policies/policy.yaml`（入 Git） | 全部可调旋钮：采集权重、单轮预算、分解阈值、终止判据、审计节奏、重试上限、检索配方、会话模式、树规模护栏、资源声明、文件请求（全量与默认值见附录 C） | P2 |
| **流程层** | `prompts/`（版本化提示词）+ orchestrator 阶段步进函数 | 四个无状态阶段的契约：触发条件 / 读取 / Codex 任务 / 产物协议 / **在阶段边界调用门禁** / 失败语义（§3） | P3 · P6 |
| **资产层** | `db/research.sqlite`（WAL，结构化唯一真相）+ 文件系统（非结构化）+ `views/`（Git 仓，DB 投影） | 唯一真相 + 双底座存储 + **门禁写库 primitive（gate/write 唯一写服务）** + 状态机 + 不变量 + 卡片层与索引 + 文件布局与缝合（§4 / §5） | P1 · P5 |
| **运行层** | `orchestrator/`（守护进程或 cron 步进） | 编排器（确定性循环驱动）+ Codex Runner 适配器（无状态工人可替换）+ watchdog + 预算台账 + 人类控制台 + **失败即观测落库**（§4） | P4 · P6 |

资产层是 **DB + 文件双底座**（§1.1.3）：结构化状态唯一真相在 SQLite，文件管非结构化内容、由 DB 索引校验（落地见 §5）。

### 2.2 元循环总览

**稳态单元 = 一个 CYCLE**。**攻坚类轮**（attack / reuse_only / eval_only）闭环回答一个问题；**cycle 本身是调度与审计核算单位**——另几类 route（bootstrap / decompose / goal_amend / dependency_wait）只推进出题 / 拆解 / 目标改版 / 等待，**真实消耗一个 cycle 但不直接回答问题**（§2.3）。攻坚轮节奏为：

```
idea(Qn) → plan(Qn) → bundle(Qn) → reasoning(答 Qn · 选/创建 Q(n+1) · 收尾)
```

- **reasoning 在轮尾**：既解释本轮 bundle 产出的证据、对本轮问题 Qn 下结论，又为下一轮**选择或创建** Q(n+1)（可选已有 open / 可 decompose / 可 terminate），并完成本轮收尾。执行阶段（bundle）只生产证据，所有裁决统一收口在 reasoning——「解释与下结论单点收口」。
- **首轮特殊**：第 1 轮没有"上一问题"可答，reasoning 仅承担"出首题"。完整序列：`reasoning(出 Q1) → idea(Q1) → plan(Q1) → bundle(Q1) → reasoning(答 Q1 + 出 Q2) → …`。
- **无独立 closing 阶段**：收尾动作（渲染 cycle_report、增量渲染 views/、Git 提交视图仓、LEDGER 记账、通知钩子）并入 reasoning 末尾（§3.5）；dependency_wait 轮不作答、不选题，由 plan 阶段机械收尾（§4.2.5），其提交后动作口径同 §3.5.4(b)。

### 2.3 route 派生：从 selection 到本轮形态

两件事**分开**：reasoning 轮尾只输出 `selection`（鸟瞰即 **选哪个问题 + 想干什么**——目标 + 意图；字段细节见 §3.5 / §5）；**本轮 `cycle.route` 由编排器据 selection + plan 结果确定性派生**，reasoning **不直接写 route**。派生规则按顺序短路、穷举互斥：

```
1. 首轮无"上一问题"（树尚不存在）        → bootstrap   （仅出首题；先于 goal_amend：无 open 可重评，启动前的目标修订并入初始 goal——goal v1 由编排器初始化自研究目标书建立，§4.6.7）
2. 有 pending 硬 goal_amend             → goal_amend  （reasoning-only：消费改版 / 重评 open / 适用性审计）
3. selection.intent = terminate        → 停机出环，无 route（§4.4）
4. selection.intent = decompose        → decompose   （reasoning-only：对选中的超预算问题写子问题）
5. selection.intent = attack → 本轮起手 route = attack（攻坚外层形态）；plan 跑完据结果**特化**为子形态：
     · plan 本轮新写未满足 question_dep（须先答他问题 / 等 baseline building）→ dependency_wait（写 dep 后收尾）
     · plan 判定 targets 为空（纯复用）   → reuse_only  （跳过 bundle，reasoning 引历史 evaluation）
     · plan 判定 targets 仅免训练评估     → eval_only   （bundle 只跑 eval、无训练）
     · 否则（有 build/exec target）        → attack      （完整 idea→plan→bundle→reasoning）
   注：idea 全不合格 / plan 缺陷 / bundle 越界等**阶段失败不改 route**——route 保持本轮已定形态，
       结局经 cycle.status=done + Qn inconclusive 表达（§3.2 / §4.2），不新增 route（故派生树穷举；本矩阵只覆盖 selection 驱动的研究轮，M4 物化 worker cycle 的形态见 OPEN #6）。
```

| route | 触发（上表） | 该 cycle 做什么 |
|---|---|---|
| `bootstrap` | 规则 1 | 仅 reasoning 出首题（无 idea/plan/bundle、无 answer） |
| `goal_amend` | 规则 2 | reasoning-only：消费目标改版、重评 open、建适用性审计（§4.6） |
| `decompose` | 规则 4 | reasoning-only：对选中的超预算问题写子问题，下轮攻坚某子问题 |
| `dependency_wait` | 规则 5·等待 | plan 本轮新写 question_dep（→问题 / →baseline）后收尾 |
| `reuse_only` | 规则 5·纯复用 | 跳过 bundle，reasoning 直接引用历史 evaluation、或 child_answer / satisfied-dep answer（父问题聚合轮）作证据 |
| `eval_only` | 规则 5·仅评估 | bundle 只跑 eval（target_kind=eval），无训练 |
| `attack` | 规则 5·否则 | 完整 idea→plan→bundle→reasoning 攻坚 Qn |

- **`terminate` 不是 route**：它是 `intent` 触发的停机决定（规则 3），见 §4.4。
- **`engineering_blocked` 不是 route**：它是 `attack` 轮内某 `build_target/run` 的结果状态，由轮尾 reasoning 裁决、把 Qn 记 inconclusive 收尾（§3.4 / §4.2）。
- `bootstrap / goal_amend / decompose / dependency_wait` 都**真实消耗一个 cycle**（有 cycle_report、有收尾），只是不进入完整攻坚四阶段——与 §2.2"cycle 是调度核算单位"一致。
- **`dependency_wait` 专指"本轮新写 dep 后收尾"**：而**已有 pending `question_dep`**（→问题 / →baseline）是**调度可见性规则**（§4.2）——带未满足依赖的问题**根本不被选中、不开 cycle**，不是一种 route。

### 2.4 召回与上下文入口

reasoning（及各阶段）的输入**聚焦本轮**（本轮问题卡 + 本轮 bundle 结果），历史信息靠**资产召回**按需取回、而非全量塞入——这是长程不漂移、单轮延迟短的关键。召回是**渐进四级**功能（流程见 §3.6.2）；其索引构建 / 查询 / 失效机制见 §4.5（Context Compiler）。

## 3 元循环执行流程

> 本章按"怎么跑一轮"的时间线展开四阶段（idea→plan→bundle→reasoning）的**流程与重点设计**，外加跨阶段能力（搜索 / 召回 / import / evaluation·control）。每阶段"怎么保证跑对"的门禁 / 状态机 / 失败语义见 §4，对象与契约见 §1；本章只讲"怎么跑"。

### 3.1 阶段 IO 与准入点地图

**3.1.1 四阶段 IO 表。** 每阶段的输入 = 固定锚（任务关键集必含、不截断）+ 检索区（按配方召回）；输出 = 经门禁入库的产物。

| 阶段 | 输入（固定锚 + 检索） | 输出（门禁入库） |
|---|---|---|
| **idea** | 选中问题卡 + 祖先链 · 该问题已试 idea 及结局（防重复造轮）· 相关已关闭结论（带 applicability 徽标，§4.5.1）· 相似失败卡 · 文献检索 | `idea_set.json` + md → IDEA + DECISION（全部候选与审计评分入库） |
| **plan** | selected idea + 验证需求 · 单轮预算 B(t) · 依赖基线卡 · 规格召回三层池卡 · 相似协议卡 | `plan.json` + md（needs / reuse_evidence / targets(target_kind) / **import_defer?（deferred 决定，不入 targets、不产 target，§3.3.1）** / 评估协议 / metric_defs / readout_rules）→ protocol + 占坑 + build_target 队列 **+ import deferred 业务三写入（命中时；并与 set_route(dependency_wait)、Qn 释放回 open、mark_cycle_done 同一事务，§3.6.3/§4.2.5）** |
| **bundle**（逐目标串行） | 计划切片 + 评估协议 + identity 模板 + env 锁 + 依赖基线 identity · 同 failure_kind 失败卡 | metrics / identity 草稿 / variant(config+overrides) / checkpoint(s) / run(build\|exec\|import，import 仅 M4 物化) + evaluation + attempt + metric_result + **execution_log/execution_observation（每 run/attempt：log ref + 结构化观测）** → **复制入池** |
| **reasoning**（轮尾） | 本轮问题卡 + **本轮 bundle 结果（含运行观测摘要：`execution_observation` 的 nan/发散/loss 趋势/warning/wall_clock）** + 目标全文 + 子树摘要卡 + directive + 召回（相似结论[带 applicability 徽标，§4.5.1] / 可对比 evaluation） | answer（仅 answered/refuted 时产；首轮 / inconclusive 不产 answer 行，只写 tree_ops/decision/失败卡）/ tree_ops / selection → 关问题 + 写树 + DECISION；收尾 = cycle_report / views / Git / 记账 / 通知 |

> **统一可选 sidecar（四阶段皆适用）**：任一阶段确实无法自行获取推进所需资料时，可在主产物旁输出 `resource_request.json`（文件请求单，schema 见《第二部分》§6.11：条目必含已尝试路径 + 失败原因）。**主 artifact 因缺资料缺失但 sidecar 合法 → 不计 `artifact_parse` 失败重试**，编排器经 `interaction_request_create` 落请求单并进入全局等待（§4.6.8），恢复后该阶段从检查点重跑。sidecar 不是研究事实、不经 Gate 三级校验入研究库。

**3.1.2 运行日志作分析输入（issue ①，不作证据）。** bundle 每个 run/attempt 除 metrics 外登记 `execution_log`（训 / 评**产物**：原始日志 + 曲线 / event / csv 等；及 smoke / stderr raw log 的 ref+hash）+ `execution_observation`（结构化观测：nan/发散/oom/warning/retry/last_loss/loss_trend/wall_clock；**机器事实仅确定性 parser 写，codex 摘要只存 `digest_ref+digest_hash`、不得冒充观测事实**）。reasoning 的固定锚带**本轮运行观测摘要**（由上下文编译器从 `execution_observation` 渲染，不塞全量 log）；据此解释指标可信度、失败模式、下一步出题。全量 raw log 与训练 / 评估产物（曲线 / event / csv 等）是冷数据，按 `execution_log.ref` 经 ctx-fetch 深潜（§3.6.2 第 4 级）；产物经只读视图 `v_metric_result_trajectory` 从 metric_result 一跳可达，供 **reasoning 综合判断**（指标可信度、失败模式、为何失败的定位），不止看终值。**铁律：raw log / 训练评估产物 / 观测内容永不作正向 evidence、不进 metric_result、不直接作 gate 判据**（I3 不变）；但 parser 据观测**确定性派生**的负向谓词 `parser_result_suspect`（§4.3.1）**仅作负向过滤**（挡复用 / 挡关问、不支持结论）——log / 观测本身只影响「解释 / 是否可信 / 下一步问什么」；若观测显示 nan / 异常，合理动作是把该 evaluation 标**结果存疑**→ 喂 plan 走复现 eval（§3.3.1 情形三）、或结论**证据不足**，**而非用 log 直接回答问题**。何为「不理想 / 存疑」的阈值在 `policy.yaml`。**`结果存疑` 不是隐藏门禁**：它只由 parser 可复算的 `execution_observation` 字段 + policy 阈值置位，本身**不是 evidence / metric_result**——只触发复现实验或阻止结论、**不支持结论**，关问题仍须回到 metric_result 有效证据（I3）。运行观测摘要进 reasoning 锚点后**只影响调试 / 复现 / 下一步评估计划，不得作 novelty / success / correctness / 关问题的选择输入**（防 log 经 reasoning 间接绕过门禁）。

**3.1.3 每阶段独立审计契约。** idea / plan / bundle 各设独立审计/评审会话：契约 = **只见产物与上游契约、不见生产过程**，评分写 DECISION(actor=judge)。实现上优先在阶段会话内 spawn Codex 子智能体；运行时不支持则回退编排器侧独立 Runner 调用。旁路产物也必须过同一审计门。**idea 审计沿用 wildidea 判官口径**：独立上下文，只收到「用户问题 + 源域名 + 目标域名 + 对象映射 + 共享关系」（看不到生成过程与源域锚点库），按 6 维 0–10 打分——Structural Depth / Domain Distance / Applicability / Novelty / Unexpectedness / Non-Obviousness；**Structural Depth 低于阈值（默认 SD<6）即淘汰**，不得生成者自评。

**3.1.4 准入点地图（哪个阶段触发哪些门禁）。** 每阶段产物经**同一写库服务**的门禁入库（机制与拒绝判据见 §4.1，状态迁移见 §4.2）；本表只给"阶段→准入点"的定位索引：

| 阶段 | 主要准入点（gate_*） | 落库对象 | 详见 |

| **idea** | 审计判官（质量裁决 actor=judge，**非门禁**）→ 经写库 gate 落 IDEA/DECISION | idea（全部候选含 failed/bypass）、decision | §4.1 |
| **plan** | `gate_new_protocol`(I1) · `gate_claim_baseline/variant`(I5) · build_target 队列 + `build_target_required_metric` · `record_question_dep`(本轮新写依赖→dependency_wait) · **import deferred 业务三写入**（M1–M3：`external_import(selected_for_materialization)` + 占位 `baseline(planned)` + `question_dep(pending)`——与 set_route(dependency_wait)、Qn 释放回 open、mark_cycle_done 同一 phase_commit 事务；业务门禁核占位状态 planned / provenance='external_import' / license_status='allow'，§3.6.3/§4.2.5） | protocol、baseline/variant(planned)、build_target、question_dep、**external_import（+占位 baseline）** | §4.1 / §4.2 |

### 3.2 idea（wildidea 跨域迁移 + NEED 分支）

**3.2.1 概念：idea = 出题 / 假设生成，分两部分。** idea 阶段为选中问题产候选想法（**不成结论来源**；novelty 只写"粗查 / 待人工验证"）。流程**分两部分 = 生成（NEED 分支：wildidea 发散 ｜ 旁路现成）＋ 独立审计（统一判官裁决）**。

**3.2.2 流程（按流程图 03-Idea；直接复用 wildidea；issue ③）。** idea 阶段**先加载 IN**（§3.1.1 idea 行：Qn 卡 + 祖先链 + **该问题全部已试 IDEA 及结局**[防重复造轮] + 已关闭结论 + 相似失败卡 + 文献检索权限），再**判「需要全新创新吗?」**（自行判断是否需大幅创新），分两条生成路、汇一个统一审计：
- **需要发散** → **wildidea 跨域机制迁移**生成（一次 `runner_call.phase=idea`）→ **自评筛选前 3**；
- **无需重大创新** → **旁路**：直接给出单一现成想法（**不跑 wildidea 发散**），仍补「源域机制 / 去锚点退化物 / novelty_type」字段供审计；
- 两路产物都进 **统一独立判官**（一次 `runner_call.phase=audit`，§3.1.3 的 6 维 0–10、SD<6 淘汰，只收映射包、看不到生成过程）→ 合格选定 1 个；全不合格则阶段失败（研究轮正常收尾 **cycle=done**（§4.2）、问题置 `inconclusive`（非终态、visit+1、可重调度），下一轮 reasoning 裁决换 idea / 降级 / 分解）。

**3.2.3 wildidea 引擎复用与跨域迁移 pipeline。**「需要发散」时的 wildidea 生成**直接 vendored 现成算法为引擎**（外包一层 `idea_engine_adapter`，**不重写机制**：复用槽位抽取 `pick_domain_slots` / 联网查重 search-integration / 6 维判官 prompt / `validate_poster` 去锚点禁词校验），其跨域机制迁移 pipeline：
1. **源域冻结**：先抽外域机制（输入/状态/输出/反馈 + 触发条件/阈值/边界），给原型编号（P01…），**冻结时禁出现用户领域禁词**（任务名/数据/指标/常规方法名）；冻结后才映射到研究领域。
2. **去锚点审查**：每条候选写「源域原型（不含领域术语）→ 用户领域怎么干（拿什么数据、按什么顺序、什么条件触发、触发后改什么）→ 去锚点退化物 → 去锚点成立等级（不成立/部分成立/成立）」；退化后只剩命名差异/普通组合 → 淘汰。
3. **三层查重 novelty**：词面查重（同名方法/模块）· 机制查重（同 I/S/O/F 不同名）· 退化查重；加最近邻差异（相同点/不同点/被吃掉风险）+ 最强反驳（审稿人视角）+ 最小可证伪实验（带对照与失败判据）。
4. **新颖性诚实纪律**（与 P4 一致）：联网/文献粗查只写「联网粗查已启用；文献级 novelty audit 待人工验证」，**绝不**把「未检索到同名」写成「查重通过」；搜索不可判定的候选不进最终集。
5. 研究类候选保留字段（进 `idea_set` 产物，见 schemas/）：原型ID · 源域机制原文 · 源域 I/S/O/F · 源域原型 · 用户领域怎么干 · 改变的算法环节 · novelty 类型（评估协议/训练目标/表征结构/推理机制/部署策略/数据准入/采样/校准/路由/损失）· 去锚点等级与退化物 · 最近邻同异与风险 · 最强反驳 · 最小可证伪实验 · 6 维评分 · 验证状态。
6. **直接复用、不大改（issue ③）**：meta-research 唯一适配 = ① 跳过 HTML 海报、只产结构化 `idea_set.json` 喂 gate；② `--forbid-proto-term` 禁词从本问题任务词注入；③ selected idea 喂 plan；④ 诚实纪律对齐 P4。**机制不重造、创新仅限 I/O 接线**（是否需大幅创新由 §3.2.2 开头 NEED 分支逐题判）。
7. **vendored 引擎的隐藏上下文必须入账（护 P1/P3/P6）**：wildidea 自带锚点库 / 缓存 / 联网结果 / 随机性 / prompt 版本——必须记 `engine_version` / `adapter_version` / `prompt_hash` / `judge_prompt_hash` / `anchor_pack_hash` / `input_card_hash` / `model` / `sampling 参数(seed,temperature)` / `dependency_lock_hash` / `policy_yaml_hash` / `retrieval_provider_version`（落 `idea.audit_json`）；**联网查重结果须作内容寻址快照入库**（query / provider / 时间 / result ids / titles·snippets·content_hashes / ranking / policy_hash，**非仅外部 ref**，否则破 P6 可回放）。SD<6 阈值 / 候选数 / 查重预算 / 禁词来源等旋钮全在 `policy.yaml`（P2）。

**3.2.4 判官口径与选择确定性。**
- **判官与选择确定性**：「SD」= 6 维之一的 **Structural Depth** 分（0–10），`SD<6` 即该维分低于阈值 → 淘汰（**非标准差 / 离散度**）；判官输入 = 映射包，失败动作 = 重做映射或淘汰。多个 idea 过线时，selected **先按审计分排序**、seed 只用于生成 / 完全同分 tie-break（**不让 seed 压过审计分、不让 Codex 临场挑**）。
- **统一审计输入契约 + 防复造入账（对齐 03-Idea 的 IN 与 ③）**：**所有候选**（含 bypass）必带 `audit_mapping`（源域 / 目标域 / 对象映射 / 共享关系）——bypass 的「源域」= 现成方案来源 / 目标域基线 / 近邻先例（DD 通常低分），wildidea 完整 I/S/O/F 仅作**额外字段**（`wildidea_extra`，非所有路径硬要求）；**统一门口径（不给 bypass 另设阈值）**：bypass 的 DD / novelty 可诚实低分，但**低 DD 不作 `need_innovation=false` 路径的自动淘汰理由**——判官用同一 6 维、判「是否适合当前 NEED」，不强制奖励新奇度；**自评筛选前 3 属生产侧 `phase=idea`、不是判官、不写 `DECISION(actor=judge)`**，独立判官 `phase=audit` 才写 judge DECISION。**gate 必做：全部候选及结局（含 failed / bypass）写 IDEA 表**（防重复造轮的关键边，不止 selected）。plan 只消费 **normalized selected**（candidate_id / core_claim / mechanism / assumptions / min_falsifiable_experiment / audit_mapping / novelty_refs；wildidea 专属字段可空）。

**3.2.5 wildidea 跨阶段调用契约（一个引擎、多个受控调用点）。** 引擎与判官不重造（§3.2.3）；各调用点职责与边界：
- **idea（主场，现状不变）**：完整 pipeline + 6 维判官 → IDEA 表。
- **decompose 轮（开放；软约束，执行点 = reasoning skill 提示词 + policy 开关）**：reasoning 会话内经同一 `idea_engine_adapter` spawn 子调用（§3.1.3 先例）产**拆分框架候选**；输出只进 `decision.payload_json` 作 rationale，子问题文本由 reasoning 定稿、经 `apply_tree_ops` 写入；**不过 6 维判官**（拆分不是 novelty 主张），质量由树规模护栏 + 后续轮证据兜底。
- **reasoning 出新题子步（窄开；同上软约束）**：仅限 `spawn_question` 的候选表述助产；**严禁进入解释证据与关问子步**——wildidea 输出不得作 novelty / success / correctness / 关问题的选择输入（与 §3.1.2 运行观测隔离同构）。
- **plan（禁用）**：协议设计保守优先；plan 若无从设计实验 = idea 不合格，走「本轮收尾、下轮换 idea」（§3.4.2 plan 缺陷路径的对偶），创造性回流上游。

**跨调用点硬边界**：① wildidea 输出一律是候选素材，**永不映射协议 / targets / selection 三个权威产物**（分别由 plan / 编排器 / reasoning 独占）；② 进 IDEA 必过统一判官（含 bypass，§3.2.4）；③ 非 idea 阶段调用的引擎溯源 hash 组（§3.2.3(7) 全清单）落 `decision.payload_json`（护 P6 可回放；idea 阶段照旧落 `idea.audit_json`）；④ 各调用点开关与预算为 policy 旋钮（附录 C idea 节 `cross_phase`）；⑤ **审计归属**：跨阶段助产调用**不新增 `runner_call.phase` 枚举**（DDL CHECK 冻结）——若起独立 runner_call 则用**调用方 phase**（如 `phase='reasoning'`）+ `purpose ∈ {'wildidea_decompose_assist','wildidea_spawn_assist'}`（purpose 为自由文本列，DDL 兼容）；会话内 spawn 不另起 runner_call 时，审计完整落父 reasoning 调用的 transcript + `decision.payload_json`。**`min_falsifiable_experiment` 是 plan 的输入素材、不具约束力**——协议 / 指标 / target 一律由 plan 依 §3.3 重新推导。

### 3.3 plan（复用判定 + import 三闸入口）

**3.3.1 plan 复用判定 → 产出 targets[]。** plan 对每个验证需求机械执行复用决策，把要执行的事写成 `plan.json.targets[]`（每项一个 `target_kind`）；**三闸命中的 import 不入 targets[]**——写 `import_defer`（deferred 决定，触发 §3.6.3 业务三写入（并与 set_route(dependency_wait)、Qn 释放回 open、mark_cycle_done 同一事务，§4.2.5），不产 build_target）：

| 情形 | 处置 | target_kind | 成本 |
|---|---|---|---|
| 池中有：同评估协议@版本 + 所需指标已测(查 metric_result) + env 兼容 | 直接引用历史 evaluation 作证据，**不产 target** | —（零执行） | 零 |
| 池中有：协议场景升版 / 所需指标尚未测 | 拿既有 checkpoint 免训练重评（场景升版→新 evaluation；同协议@版本加指标→同 evaluation 追加 attempt） | **eval** | 低 |
| 池中有：env 失配 / 结果存疑 | 复现性 eval（执行 identity 复现命令，不重建 checkpoint） | **eval** | 低 |
| 池中无，且实验角色＝在我方结构内自建（消融 / 模块替换 / 改超参 / 改评估） | 自建路径（**不 import**）；身份按 §1.2.2 判定——改设置 = 新 variant，前向逻辑 / 结构种类拓扑变（非头数 / 层数 / 维度等规模参数）= 新 baseline（parent 指原） | **build / exec / eval** | 中 |
| 池中无，且实验角色＝引入**新 baseline 家族 / 外部参照槽**（comparator / 公认 SOTA / 人点名 repo） | 走 import 准入链（§3.3.2 三闸 / §3.6.3 准入链；**M1–M3 仅记 deferred decision、不进 bundle**） | —（**import_defer** deferred 决定，非 target；M4 物化 worker cycle 才建 `build_target(import)`，§3.6.3） | 高 |

- **`targets=[]` ⇔ 纯复用轮（`route=reuse_only`）**：不进 bundle，reasoning 直接引用历史 evaluation。`reuse_evidence` 亦可为 child_answer / satisfied-dep 的 answer——父问题聚合轮（全部子依赖 satisfied 后据子答案关闭，§4.2.4 `add_children`）不产生验证需求、天然 `targets=[]`。
- **`targets=[{eval}]` ⇔ 免训练评估轮（`route=eval_only`）**：**仍进 bundle**执行评估，只是不训练。
- 复用判定**查 metric_result 覆盖**，不能只看 evaluation 是否 success——协议追加新指标后，旧成功 evaluation 未必含该指标结果。
- 协议三种变化分清：**场景变**→新 `protocol.version`；**加指标**→append `protocol_metric`（不升版）；**指标计算/判读变**→新 `metric_def.version` 再 append。

**复用判定 = 机械 selector**（**规范 SQL 见 §4.1.5**，含结果存疑过滤）：逐 required `(metric_id, metric_ver)` pair 核 `metric_result` 覆盖（命中取 canonical / 最新 success attempt）+ `env_hash` 精确相等 + 排除 `parser_result_suspect`（派生谓词）为真的 attempt；**命中** ⇒ 零执行引用历史 evaluation，**缺任一** ⇒ 落 eval/exec/build target。判定契约：
- **命中**：每个 required `(metric_id, metric_ver)` pair 都至少返回一行；缺任一 → 不复用、落 target。
- **同一 `(metric_id, metric_ver)` 多行**（canonical + `metric_append`/复现 attempt 都测了它）：`rk=1` 自动取 canonical attempt、其次最新 success attempt（`ORDER BY canonical DESC, attempt_no DESC`）——**metric_append 引入的新指标允许作复用证据**。
- **env 兼容硬判据**：`env_hash` 精确相等；不等不复用，走情形三（复现 eval）。
- **结果存疑前置过滤（与 §3.1.2 一致）**：parser 据 `execution_observation` + policy 阈值**派生**谓词 `parser_result_suspect`（**非存储列**，§4.3.1）；存疑 attempt **不作复用证据**、落情形三复现 eval。它本身**不是 evidence/metric_result**，只挡复用 / 关问、不支持结论。
- **不可只看 `evaluation.status='success'`**：必须逐个 required `(metric_id, metric_ver)` pair 核 `metric_result` 覆盖（协议追加指标后旧 evaluation 未必含新指标）。

**plan 产出的 `target_kind ∈ {build, exec, eval}`**：build=新 baseline 构建；exec=新变体训练；eval=免训练评估（不建 run 行、审计落 `evaluation_attempt`，见 §4.2.1）。**`import` 枚举位（`build_target.target_kind` / `run.kind`）为 M4 物化 worker cycle 预留、plan 不产**——import=引入外部开源 baseline 的 pipeline（发现登记→确定性选择→license→物化→出厂 eval→pool_publish，非单步；见 §3.6.3）：M1–M3 plan 只写 deferred import decision（`import_defer`，《第二部分》§6.11）+ 占位 baseline + question_dep、不产 target 不进 bundle，**M4 物化才产 `run.kind=import`**。`run.kind ∈ {build, exec, import}`（口径详 §3.6.4）。**eval target 必带 `eval_action ∈ {create_evaluation, append_attempt}` + `attempt_purpose`**：同 (variant, protocol@版本) 已有 evaluation → `append_attempt`（追加 attempt、不新建 evaluation，带 evaluation_id）；无 → `create_evaluation`（建 evaluation + 首 attempt）。**评估协议在 plan 锁死，bundle 只照办**（I2 源头）。占坑互斥（I5）防昂贵构建重复开工。

**3.3.2 自建 vs 外部 import：三闸（决定要不要 import；issue ②）。**「池中无对应能力」不再一律自建；先过三闸决定要不要引入外部开源 baseline（别造轮子），命中则走 import 准入链（pipeline，见 §3.6.3）。
- **闸1 类型门（按实验角色，非拓扑新旧）**：目标是「在我方结构内做局部干预 / 消融 / 模块替换」→ **internal 自建路径**（**即便拓扑变也不 import**——是否 import 看"是否引入外部实现"、与拓扑无关；自建后**身份按 §1.2.2**：改设置 = 新 variant、前向逻辑 / 结构种类拓扑变（非规模参数）= 新 baseline，不强归同 baseline 的 variant）；目标是「引入一个独立 comparator baseline 家族 / 公认外部参照槽」→ import-eligible。（把外部 baseline 当**地基**迭代亦走 import 引入该家族，之后在其上的迭代是 internal 自建。）
- **闸2 状态门（只读、不越权）**：question 连续若干轮验证不理想（`visit_count` 高、反复 inconclusive，阈值在 `policy.yaml`）→ 触发一次**只读外部普查**；普查产物只能**生成新 candidate idea 或新 question**，**不得在原 variant/eval question 上直接触发 import 准入选择（import_defer）**。只有当新 question 被确定性重分类为「缺失外部 baseline / 新 baseline 家族」，才进 import 选择。
- **闸3 规模缩放**：外部普查的活跃度 / 预算随 question 规模（`est_cost`/`score`）+ `B(t)` 动态调（`policy.yaml` 旋钮，P2）；大 / 贵问题给足普查，小问题几乎不搜。
- **两个直达场景（只绕发现门、不绕准入门）**：① 人点名某 repo（directive→`human_named`）→ 绕闸1，但**仍过** license / pinned revision / manifest / smoke / I4 / M4 物化；② 对照实验缺**公认 SOTA**（`sota_reference`）→ **只生成 baseline-reference / import 问题、不污染原 variant 问题**，且「公认 SOTA」须 frozen paper/benchmark 快照（**非 latest**）。

> 三闸只决定"要不要 import"；命中后的 `发现登记 → 确定性选择 → license → 物化 → 出厂 eval → pool_publish` 准入链（pipeline）见 §3.6.3，其门禁（I4/I6）见 §4.1。

### 3.4 bundle（逐目标执行 + 自愈边界）

**3.4.1 概念。** bundle **逐目标串行**执行 plan 锁定的 `targets[]`，**按 `target_kind` 产适用对象**（build/exec → run + checkpoint + evaluation + attempt + metric_result；eval → evaluation + attempt + metric_result、**不建 run**；import 非 plan target、不进研究轮 bundle（M4 物化 worker cycle 专属，§3.6.3）；口径详 §3.6.4）+ 运行日志（§3.1.2）。build/exec 主链 = **构建 → smoke → 代码适配评审 → 训练 → 出厂评估 → 结果评审 → 三级校验 → 注册入池**；eval 免训练，= 评估 → 结果评审 → 三级校验 → 注册（两道评审的对象与判据见 §3.4.3）。**评估协议 plan 已锁、bundle 只照办**（I2 履约）；逐目标**两段提交**（执行事实随发生短事务入账、结果评审通过后测量注册单事务，§4.2.5）、目标间不共事务，崩溃从 `bundle_cursor` 续。

**3.4.2 自愈边界。** 工程问题（代码 / 环境 / 报错 / 依赖 / 格式 / 指标未产）在 bundle 内闭环自愈，但有严格边界：
- **只限 plan 既定下的实现问题**：无修复次数上限，只受预算 + watchdog（§4.4）约束；预算尽 → 自动追加一次 + 换会话 → 仍败则置 `engineering_blocked` + 通知人。**工程失败永不入问题树**（它不是研究结论）。
- **engineering_blocked 如何回元循环**：该 build_target 置 `engineering_blocked` 并通知人；轮尾 reasoning 把 Qn 记 `inconclusive`(visit+1)、写失败卡与 DECISION，但**不关问题、不入研究证据**。人修复环境后**不复活旧 target**——下一轮重新 plan、建新 target。依赖阻塞则写 `question_dep(pending)`，调度器暂排除该问题。
- **plan 缺陷不归 bundle**：若发现是"计划本身有缺陷"，本轮收尾、下一轮重 plan（问题 visit+1，不在轮内折返、不立新问题）。

**3.4.3 双评审边界（§3.1.3 审计契约的 bundle 实例）。** 两道独立评审（独立子智能体、独立上下文、只见产物不见生产过程），评审结论写 `DECISION(actor=judge)`，判据由 §4.1.4 门禁机械核对：
- **代码适配评审（`code_review`，仅 build/exec）**：smoke 通过后、训练前。输入 = plan 计划切片 + 代码产物（worktree diff / config+overrides / identity 草稿）+ smoke 结论；判据 = 实现与 plan 适配、无缩水、无不当实现。不过 → 评审意见回传构建会话修复后复核；轮数上限 `bundle_code_review`（附录 C，默认 3），用尽 → target `failed(review_failed)`（不训练、省成本）。通过是 `smoke→running` 迁移的前置（§4.1.4 `gate_progress_build_target`）。
- **结果评审（`result_review`，build/exec/eval 一切产成功测量的 target）**：评估产物就绪后、注册入池前。**评审对象一律是 staging 产物**（评估结果规范 artifact、checkpoint 内容哈希、运行日志与 parser 观测的 staging 文件、identity 草稿）——此刻测量行尚未进入注册段提交（§4.2.5 两段提交）；判据 = 结果与日志合理（量级 / 曲线 / 异常）、据结果反查代码无明显 bug。运行日志**仅供 judge 会话读，不进 Gate 判据、不作研究证据**（§3.1.2 铁律原样）。不过 → 意见回传修复重评；轮数上限 `bundle_result_review`（默认 3），用尽 → target `failed(review_failed)`：测量整包不注册、不入池不 legal（已入账的 `run(success)`+checkpoint 是训练事实、保留），审计 = judge DECISION + 失败卡 + staging 归档——**与「评估执行失败」不同**（后者照旧写 `evaluation_attempt(failed)`，§4.2.2 口径）。
- **评审通过的机械判据**（唯一定义在 §4.1.4 表后附注）：pass DECISION 的 `subject_hash` 须等于编排器当下重算的产物集哈希，且 `runner_call` 为 `status='success'、phase='audit'、purpose=对应评审`——修复后产物变，旧 pass 自动失效。

> bundle 的失败如何不被误判成"系统失败"、各 `gate_*`/状态迁移的判据见 §4.1 / §4.2；本节只讲"自愈到哪、越界怎么收尾、评审把关什么"。

### 3.5 reasoning（轮尾：解释 · 下结论 · 选题 · 收尾）

reasoning 是元循环**裁决与作答路径**的收口阶段（轮尾；dependency_wait 轮由 plan 机械收尾、不经 reasoning，§4.2.5），一个会话内串做四件事——这是"解释与下结论单点收口"的落地：

**3.5.1 解释证据。** 读本轮 bundle 结果（含运行观测摘要 §3.1.2）+ 目标全文 + 子树摘要卡 + 召回的可对比 evaluation，解释指标可信度与失败模式。运行观测只影响"是否可信 / 下一步问什么"，**永不作 novelty/success/关问题的选择输入**（§3.1.2 铁律）。

**3.5.2 下结论（关问题，I3）。** 仅当有 ≥1 条有效 evidence（成功 `metric_result`）才对 Qn 产 answer（answered / refuted），经 `gate_close_question`(I3) 入库（判据见 §4.1）；证据不足 → **不产 answer 行**、Qn 置 `inconclusive`（非终态、visit+1、可重调度，§4.2）。answer 绑当前 `goal_ver`，evidence 多态（evaluation / literature / child_answer / human）。

**3.5.3 选题 / 写树（selection + tree_ops）。** 输出 `selection`（选下一个攻坚目标 + `intent ∈ {attack, decompose, terminate}`，§2.3 据此确定性派生下轮 route，reasoning 不直接写 route）；R3 选题对 open 集逐问题**四元打分并全程留痕**，`selection.scores[]` 经 `persist_selection` 写回 `question.score / est_cost`（唯一维护点，§4.2.4）。写树经 `apply_tree_ops`——**op 封闭词表见 §4.2.4**：reasoning-only 轮做 bootstrap 建首题 / decompose 写子问题并释放父问题 / goal_amend 建目标新版本 + 适用性审计（§4.2 / §4.6）；**攻坚轮尾亦可 `spawn_question`（诊断 / 后续 / 回看 / import 参照题）、`mark_answer_applicability`（回看旧结论，§4.6.4）、`propose_prune`**。**选题可选已有 open、可 decompose、可 terminate 停机**，不总是新出题。**出新题子步可调用 wildidea 助产候选表述（§3.2.5）；wildidea 输出不得进入解释证据与关问子步**（隔离与 §3.1.2 运行观测同构）。

**3.5.4 收尾（无独立 closing 阶段；本节为 reasoning 轮尾收尾，dependency_wait 轮收尾见 §4.2.5）。** 轮尾分两步：
- **(a) DB 收尾事务**：`answer + evidence → question.status → apply_tree_ops → persist_selection → mark_cycle_done` 在**单一 DB 事务**内提交（任一步失败整体回滚、下次 advance 幂等重做），**杜绝"问题已关闭但 selection 未落库"这类半写**。
- **(b) 提交后动作**：分两类——**结构化账本写入**（LEDGER 记账）是 **DB 审计账本**、可由 outbox **幂等补写**（§4.3），仍是结构化真相；**外部副作用**（渲染 `cycle_report` / 增量渲染 `views/` / Git 提交视图仓 / 通知钩子）**不在 DB 事务内、不可回滚**，作提交后幂等动作 / outbox、失败可重放。二者都不与 (a) 的 DB 收尾事务同桶（DB 事务无法回滚 Git / 通知 / 文件渲染）。

> DB 事务边界、outbox 投递与渲染/通知失败处理见 §4.2 / §4.3；本节只标"先原子落库、再幂等放副作用"。

> reasoning 的门禁判据（`gate_close_question` 的 evidence 合法性、child_answer 须当前子树或经 satisfied `question_dep`）见 §4.1；状态迁移（StateStore）、原子提交与失败语义（reasoning 产物非法 → cycle `failed`）见 §4.2。

### 3.6 跨阶段能力

> 四阶段之外、被多个阶段共用的横切能力：外部检索、资产召回、import 准入链、对照设计。它们的**索引 / 存储 / 门禁机制**在 §4.1 / §4.5 / §5；本节只讲"跨阶段怎么用"。

**3.6.1 搜索文献 / 外部检索（只读、按需触发、规模缩放）。** 系统的外部检索是**只读能力**（文献 + GitHub/代码，经只读 MCP，`runner_call.phase ∈ {idea, import_search}`），三处消费、统一规模缩放：
- **idea 阶段**：作 idea 行的检索区输入（相关文献），供 wildidea 三层查重 novelty（§3.2.3）与防重复造轮；只写"粗查 / 待人工验证"，**绝不当 novelty 结论**（P4）。
- **闸2 状态门触发的外部普查**：question 连续不理想（`visit_count` 高 / 反复 inconclusive）→ 触发一次只读外部普查；产物只生成**新 candidate idea / 新 question**，不直接触发 import_defer（§3.3.2）。
- **import 发现**：命中入库为不可变 `external_candidate` 发现快照（§3.6.3）。
- **规模缩放（闸3，P2）**：检索活跃度 / 预算随 question 规模（`est_cost`/`score`）+ `B(t)` 动态调——大 / 贵问题给足普查、小问题几乎不搜；旋钮在 `policy.yaml`（检索配方）。
- **可回放（P6）**：检索结果作**内容寻址快照**入库（query / provider / 时间 / result ids / content_hashes / ranking / policy_hash），非仅外部 ref。

> 搜索结果**本身不作 evidence**；**实验性能 / 对照类结论**须回到本系统 harness 的 `metric_result`（I3）。其余 evidence 形态（literature / human / child_answer，§3.5.2 多态）走各自门禁，搜索只是其素材来源、不绕过门禁。

**3.6.2 资产召回流程（渐进四级）。** 召回服务于"plan 的复用判定"（§3.3.1）这一最重需求。设计为**渐进四级**，由粗到细，能在哪级停就在哪级停：
1. **初筛**：语义检索 + faceted tag → 命中方法族卡 / 基线卡（v1 用纯自由 tag，不强求规整）。
2. **中筛**：读基线卡的**变体矩阵**，定位候选变体。
3. **精确**：评估协议@版本 + 指标匹配；**测量索引 `(variant_id, protocol_id, protocol_ver)` O(1) 命中成功 evaluation**。
4. **深潜**：`ctx-fetch` 按 ref 进入 `evaluations/` / `src/` / **运行日志与训练 / 评估产物（`execution_log.ref`，训 / 评 raw log + 曲线 / event / csv 等，§3.1.2）** 读原始内容。

**投影 = 三层卡片**（方法族/基线/变体），可读 slug + 能力描述指代具体资产。**反向链接（仅变体级）**：`born_question`（一对一权威：这个变体为哪个问题而生）/ `used_by_questions`（从 EVIDENCE 反查派生，物化进变体卡）。补充召回属性：`baseline.capability_summary` / `variant.result_summary` / `env_hash`。**tag 挂在 baseline 级**（方法族 / 能力维度；任务 / 数据集维度走 protocol，不走 tag）。卡片体系与召回索引的**构建 / 物化 / 失效**机制见 §4.5。

**3.6.3 import 准入链（pipeline，三闸命中后）。** 三闸（§3.3.2）决定要 import 后，走 `发现登记 → 确定性选择 → license 裁定 → 物化 → 出厂 evaluation(factory) → pool_publish`（非与 build 对称的单步 target）：
- **发现**：只读 MCP 检索（文献 + GitHub/代码，`runner_call.phase=import_search`）→ 命中入库为**不可变 `external_candidate` 发现快照**（`revision` pinned commit、`search_snapshot_hash`、`trigger_snapshot_hash`）。
- **选择（确定性，护 I6）**：**candidate_set 按 `action_cycle` 冻结**（不取「当前最新 / 累计至今」的隐式集），按 `selection_key` 序从冻结集选**第一个 license 通过**的候选，落 `external_import`。（冻结输入元组、`candidate_set_hash` / `selection_key` 规范化与审计列等**确定性机制见 §4.1**。）
- **license（append-only 裁定 + scope）**：`license_review` 记 `decision∈{allow,deny,review}` + `license_scope_json`（`allow_eval/allow_modify/allow_publish_pool/allow_redistribute`）；deny → `external_import(rejected_by_license)` → 按 `selection_key` 取下一个；物化选择基于冻结 `license_decision_snapshot_hash`，**只从 `decision=allow` 且 scope 匹配的候选选**。「可加变体」须 `allow_modify`、入池须 `allow_publish_pool`。
- **里程碑降级（M1–M3）**：import 只产 `external_candidate` 发现快照 + `external_import(selected / selected_for_materialization)` **审计状态**、**不产可执行 target、不进 bundle、不期待 pool_publish**；选择时 gate **创建 `baseline(planned)` 占位**（`external_import.baseline_id` 回指占位——CHECK 允许 `selected_for_materialization` 携 `baseline_id`，附录 A；`provenance='external_import'`、`license_status='allow'`，待物化）+ **写 `question_dep(dep_type=baseline → 该占位 baseline)`** 使问题**因 baseline 未 legal 而不可调度**（§4.2.1 调度可见性，**非新增 question.status**；`import_pending_materialization` 只是该 pending-dep 处境的描述名）——**M4 物化把该 baseline 注册 `legal`**（`gate_register_baseline`），dep 由 `baseline→legal` 规则**机械 satisfied** → 问题恢复可调度、按常规复用判定消费池中已 legal 的该 baseline（与「M0–M3 假执行」边界一致，见《第三部分》）。
- **物化（M4，由 Advancer 驱动，非靠等待问题调度）**：`Advancer` 扫描 `external_import(selected_for_materialization)` **物化工作队列**、起一个**物化 cycle**（独立入口、与等待问题解耦）：clone pinned revision → 生成 manifest（须含供应链闭包：`revision`/submodule SHAs/`patch_set_hash`/LFS·artifact hashes/dependency lock hash/`harness_adapter_hash`/build image·env hash）→ 沙箱 smoke（铁律5）→ `target_ready` → 出厂 evaluation → `gate_register_baseline`(I4，§4.1) **把占位 baseline 注册 `legal`** → `resolve_deps` 满足 `question_dep` → 原问题回 open 可调度 → pool_publish。**该物化 cycle 是内部 worker cycle**——§2.3 的 7 形态（selection 驱动的研究 route）封闭、不为它新增枚举；其 `cycle.route` 表达方式（NULL / 复用既有 / 另行）与收尾形态**未定，OPEN #6**、M4 开工前确认。
- **证据归属**：imported baseline 经**本系统 harness** 跑出的 evaluation `source` 仍为 `factory`（外部性只在 `checkpoint.origin=external_import` + `external_import.manifest_hash`），**不新增 metric source**；论文 reported 数字只作背景、**绝不作 factory 证据**。**所有 comparison / report 必须 join `checkpoint.origin` / `external_import_id` / `manifest_hash` / `revision` / `license_review_id` 显式带 provenance**——自建与导入实现不得在报表里混同。

**3.6.4 evaluation · control 设计（对照元 = evaluation）。**
- **对照元 = evaluation = 变体 × 评估协议@版本**（§1.2.2 / §1.3）：一次对照 = 在同一评估协议@版本下、对不同 variant（含自建与 imported）跑 evaluation，证据 = `metric_result`；`evaluation.source` 标证据来源（`factory` 出厂 / `protocol_upgrade` 免训重评等；**完整枚举与 `attempt_purpose` 见 §4 / §5**，本节不固死）。
- **协议锁定（I1/I2）**：评估协议在 plan 锁死（scope_spec + protocol_metric + metric_def + readout_rules），bundle 只照办、只落协议声明过的指标；协议三种变化（场景升版 / 加指标 / 计算判读变）的版本语义见 §3.3.1。
- **run.kind 与 eval 审计载体（口径）**：`run.kind ∈ {build, exec, import}`；bundle **按 target_kind 产 run**——build/exec 产 run + checkpoint，**eval 不建 run**（审计事实 env_hash / commit / transcript / watchdog / 失败 / 重试 / 成本落 `evaluation_attempt`），import 仅 **M4 物化**产 `run.kind=import`。出厂评估与免训 eval **同构**（都写 evaluation + ≥1 attempt，仅 build/exec/import 额外写 run）。失败重试 = 追加 attempt；成功 attempt 经 `canonical_attempt_id` 标定复用基准。
- **control（对照基准）**：comparator / 公认 SOTA 经 import 引入（§3.3.2 / §3.6.3），与自建在**同协议**下对照；报表必 join provenance（`checkpoint.origin` / `external_import_id` / `manifest_hash`），自建与导入不混同。
- **target 选择确定性（I6）**：同输入 → 唯一规范 target 集 + `target_set_hash`，禁 wall-clock / `latest` / 历史指标（护 O(1) 复用 soundness）；机制见 §4.1。

## 4 正确性、状态与运行控制

> 本章讲"怎么保证跑对"：写入如何被门禁强制（§4.1）、状态机 / 失败语义 / 原子提交（§4.2）、审计 / 运行日志 / 决策账本（§4.3）、运行时编排（§4.4）、上下文与资产消费（§4.5）、人机入站（§4.6）、运行旋钮（§4.7）。**对象与不变量定义在 §1、流程在 §3**，本章只讲 how-enforced。

### 4.1 写入门禁（唯一写库路径 + 三级校验 + 不变量执行）

**4.1.1 唯一写库路径。** 任何数据进入 SQLite 都必须走同一条路：

```
Codex 产物  →  三级校验  →  门禁函数 gate_*  →  写库（同一事务刷新卡片与索引）
              ① JSON schema
              ② 引用完整性（所引 id 真实存在）
              ③ 业务门禁（不变量 I1–I6；I6 经 gate+selector+审计列，非纯触发器）
```

门禁函数是**资产层唯一写库服务**（daemon 侧单一 SQLite 写连接，全部 DDL 触发器（附录 A）恒在）。写入分两族、**共用同一事务边界与触发器**：①**事实注册**（§4.1.4 `gate_*`，校验 Codex 阶段产物 idea/plan/bundle/answer，写 baseline/variant/run/evaluation/metric_result/idea/answer/evidence）；②**状态迁移**（§4.2 `StateStore`，写 cycle/route/selection/question 树/适用性，由编排器据 reasoning `selection`/人类 `directive` 驱动、非 Codex 产物）。"唯一写入口"指唯一**写服务**而非唯一函数；Codex 永不持库凭据。三级校验是"LLM 与真相之间的确定性仲裁"：schema 不合当场拒、引用悬空当场拒、违反不变量当场拒，记 `DECISION(actor=gate, type=reject)`，按策略重试 ≤2 次仍败则升级为阶段失败。

**4.1.2 MCP 只挂只读工具。** 给 Codex 会话的 MCP 工具一律只读：`ctx-fetch`（按 ref 深潜冷数据）、文献检索、`validate_artifact`（产物预检）。**Codex 没有数据库凭据、没有 views/ 写权限**，永不直接碰库。

**4.1.3 预检 / 提交分离 · 阶段内多次提交 · 长训练可恢复。**
- **预检**（`validate_artifact`）：会话内实时反馈，让 Codex 在提交前自查产物是否合 schema、引用是否完整。预检**不写库**。
- **提交**：在编排器事务内**重新**跑三级校验后才写库——预检的结论不被信任，真相侧总要再验一次。
- **阶段内可多次提交**：一个阶段内每产出一个可提交单元，就调一次门禁提交（执行者是 daemon 侧 service，不是 Codex 直写），让长阶段也有细粒度检查点。
- **长训练可恢复**：训练**进度**（checkpoint，文件）与**事实记录**（DB 事务）分离；RUN 开训即落 `running`，训练框架周期性写 checkpoint 文件；`kill -9` 后从最近 checkpoint 续训、不从头跑。

**4.1.4 门禁函数表（事实注册；M1 可实现判据）。** 每个 `gate_*` 的输入 artifact、DB 写入、拒绝判据如下（M1 据此实现，不靠猜）。失败事实（run/attempt `failed`、`engineering_blocked`）经 `finish_*` 入库，**失败入库 ≠ `cycle.status=failed`**（见 §4.2）；`gate_register_baseline/variant/evaluation` 为成功快捷路径（= 对应 `start_*`+`finish_*(success)` 合并）；**required 指标集由 plan 写入 `build_target_required_metric` 表，`gate_finish_attempt`/`gate_register_*` 据此逐项核 aggregate metric_result 覆盖**：

> **可评 target 泛化 + 门禁拆层（v2.2 终稿，并入附录 A）**：`checkpoint` 已泛化为「可评 target」（含 external_model/prompt_only/algorithm/retrieval_index）。注册门禁据此拆两层——**target_ready**（可被评估）= 每个 target `ready` + `content_hash`（外部 target 另需 `manifest_hash/source_uri/revision`）+ 复现 spec，`run(success)` **仅 `origin=run_produced` 时必需**（外部/免训练 target 无本池 run）；**pool_publish**（变体→`legal`）= 在 target_ready 之上再要求 ≥1 个 **`source='factory'`** 的成功 evaluation+canonical（出厂评估；非 factory eval 不作发布基础——与附录 A `trg_eval_no_abandon_if_cited` 的 factory 守卫对齐）。两层拆分避免「注册变体需 eval 成功」与 eval 创建成环。**`import`（run.kind / build_target.target_kind）完整 start/finish gate 流程推迟 M4**（v2.2 为预留/审计枚举位）。下表 `checkpoint(s)+hash / checkpoint 无 content_hash` 读作「target(s)+hash / target 缺 hash」。

> **附注：双评审 DECISION 的机械判据（本表 `gate_progress_build_target` / `gate_register_*` 引用的唯一定义）。** 两类评审各写一条 `DECISION(actor=judge, type=bundle_code_review / bundle_result_review)`，`payload_json` 最小必填 = `{build_target_id, review_kind, round_no, verdict∈{pass,fail}, subject_hash, runner_call_id, policy_hash}`；评审会话审计 = `runner_call.phase='audit'`、`purpose='bundle_code_review'/'bundle_result_review'`。**subject manifest 由编排器确定性构造（judge 不自算）**：canonical JSON（键排序、条目按 ref 排序）的条目数组，每条 `{kind, ref/id, content_hash}`，`subject_hash = sha256(canonical_json)`。产物集构成（规则 = 不引用未提交 DB 行）——**code_review** = plan 计划切片 hash + worktree 代码 diff hash + config/overrides 文件 hashes + identity 草稿 hash + smoke transcript ref+hash；**result_review** = 评估结果规范 artifact（fold+aggregate 指标值文件）hash + checkpoint content_hash(es)（build/exec 为本 target 新产；eval 为既有 legal checkpoint 的已提交 content_hash/id，引用已提交行合规）+ 运行日志 staging 文件 ref+hash 集 + parser 观测 staging 文件 hash + identity 草稿 hash（eval 无则省）。**通过判据** = 存在 verdict=pass 的对应 DECISION，且 ① `subject_hash` 等于编排器**当下重算**的产物集哈希（修复后产物变 → 旧 pass 自动失效，防旧评审 / 错 target / 修复前评审误放行）② 其 `runner_call_id` 指向 `runner_call(status='success', phase='audit', purpose=对应评审)`。评审语义与失败路径见 §3.4.3，轮数旋钮见附录 C `flow.retry`。

**4.1.5 复用判定 selector（规范 SQL；§3.3.1 契约的机械实现）。** 命中 ⇒ 零执行引用历史 evaluation；任一 required metric 缺 ⇒ 落 eval/exec/build target：
```sql
WITH required(metric_id, metric_ver) AS (
  VALUES (:m1_id, :m1_ver)        -- 动态展开：每个 required 指标一行 (metric_id, metric_ver)
),
ranked AS (
  SELECT r.metric_id, r.metric_ver, mr.id AS metric_result_id, mr.value,
         ROW_NUMBER() OVER (PARTITION BY r.metric_id, r.metric_ver
           ORDER BY (ea.id = e.canonical_attempt_id) DESC, ea.attempt_no DESC) AS rk
  FROM required r
  JOIN evaluation e        ON e.variant_id = :variant_id AND e.protocol_id = :protocol_id
                          AND e.protocol_ver = :protocol_ver AND e.status = 'success'
  JOIN evaluation_attempt ea ON ea.evaluation_id = e.id AND ea.status = 'success'
                          AND ea.env_hash = :required_env_hash    -- env 兼容=env_hash 精确相等（不等→落复现 eval）
                          AND parser_result_suspect(ea.id) = 0    -- 派生谓词(非列)：读该 attempt 的 parser observation(source='parser')、按其 extraction_policy_hash 固定复算，§4.3.1（改 policy.yaml 不回溯改历史可复用性）
  JOIN metric_result mr    ON mr.evaluation_id = e.id AND mr.evaluation_attempt_id = ea.id
                          AND mr.scope = 'aggregate' AND mr.metric_id = r.metric_id AND mr.metric_ver = r.metric_ver
  LEFT JOIN build_target bt ON bt.id = COALESCE(ea.build_target_id, e.build_target_id)
  WHERE (COALESCE(ea.build_target_id, e.build_target_id) IS NULL OR bt.status = 'complete')
                          -- target_complete 负向过滤：评审失败/未完成 target 的成功测量不可作复用命中（§4.1.4 附注）；
                          -- NULL 仅限非 bundle 的 M4 import 物化来源（bundle 路径的绑定由 gate 强制，§4.1.4）
)
SELECT metric_id, metric_ver, metric_result_id, value FROM ranked WHERE rk = 1;
-- 命中 = 返回行覆盖全部 required (metric_id, metric_ver) pair；缺任一 → 不复用、落 target。
```
- **同一 `(metric_id, metric_ver)` 多行**（canonical + `metric_append`/复现 attempt 都测了它）：`rk=1` 自动取 canonical attempt、其次最新 success attempt——`metric_append` 引入的新指标允许作复用证据。
- **env 兼容硬判据**：`env_hash` 精确相等；不等不复用，走复现 eval。**结果存疑**：`parser_result_suspect` 为真的 attempt 不作复用证据（**parser 派生谓词、非存储列**，§4.3.1）。**target_complete**：所属 build_target 非 `complete` 的成功测量不作复用证据（负向过滤，§4.1.4 附注；`gate_close_question` 同判据）。
- **不可只看 `evaluation.status='success'`**：必须逐个 required `(metric_id, metric_ver)` pair 核 `metric_result` 覆盖（协议追加指标后旧 evaluation 未必含新指标）。

**4.1.6 target 选择确定性（I6）：普通 target + import。**
- **普通 build/exec/eval target（plan/bundle）**：plan 用**规范化 selector** 产出唯一规范 target 集（输入禁 wall-clock / `latest` / **按历史性能值或排名选 target**；**复用判定查 `metric_result` 覆盖不在此列**——那是"是否已测"的覆盖判定、非按性能挑 target），算 `target_set_hash`，经 `gate_register_evaluation` / `gate_start_attempt` 写入 `evaluation.target_set_hash`（INSERT 写入、身份冻结、审计列）。**hash ↔ 实际消费集的完全校验经薄表 `evaluation_target` / `attempt_target` 落地（推迟 M4，附录 B）**；v2.3 阶段 I6 = selector 规范化 + 审计列写入（非纯触发器）。
- **import 准入选择（三闸命中后，`import_defer`）**：选择须确定性可回放——冻结输入元组 = `(question goal_ver, action_cycle, trigger_snapshot_hash, candidate_set_hash, license_decision_snapshot_hash, policy_hash, selection_key)`（内容寻址；纳入 `license_decision_snapshot_hash` 使 `license_review` 后续 append 不漂移历史选择）；**candidate_set 按 action_cycle 冻结**（不取"当前最新 / 累计至今"隐式集）；按 `selection_key` 序选第一个 `license_review.decision=allow` 且 scope 匹配者，落 `external_import`（deny → 取下一个）。
- **审计三表**：`external_candidate`（发现快照）/ `license_review`（append-only 裁定 + `license_scope_json`）/ `external_import`（选择事件含上述 hash）——回放即重算同一选择；import 物化出厂 eval 的 target 集同样进 `target_set_hash` 身份冻结。

**4.1.7 不变量执行映射。** 不变量 I1–I6 + append-only 的"准入点 → 门禁 → 存储"映射见 **§1.5**（契约执行索引）；本节 §4.1.4 是 I2/I3/I4/I5 的门禁落点、§4.1.6 是 I6 的落点、I1 落 `gate_new_protocol`、append-only 落 §4.2 终态冻结触发器（附录 A）。

### 4.2 状态机、失败语义与原子提交

**4.2.1 状态机总览（对象状态 + 调度可见性）。** 各对象状态机（CHECK 约束 + 迁移触发器详**附录 A**）：
- **baseline / variant**：`planned → building → legal → deprecated`（失败旁路 `build_failed`；**`abandoned` = planned/building 放弃**，如 claim 后未建、import 占位未物化）。`evaluation` 自己的 `abandoned`（`gate_abandon_evaluation`）是另一回事，不动 baseline/variant。
- **run**：`created → running → success/failed`（终态冻结、append-only）。**evaluation_attempt**：`created → running → success/failed/aborted`（终态冻结、append-only；`failed` 须带 `failure_kind`）。
- **evaluation**：`created → running → success/failed/abandoned`。
- **build_target**：**build/exec** `pending → building → smoke → running → complete`、**eval** `pending → running → complete`（免训练，无 building/smoke；旁路 `skipped/failed/engineering_blocked`——`failed` 含双评审轮数用尽的 `review_failed`，其中代码适配评审失败走 `smoke → failed`；**合法链唯一定义即本条**、由 `gate_progress_build_target` 代码兜底，附录 A 仅枚举 CHECK；评审前置判据见 §4.1.4）。
- **cycle**：`… → done/failed/aborted`（route 去 `failed`，见 §2.3）。
- **question**：`open ⇄ active`，关闭 `→ answered/refuted/dead_end`（**终态 = 三者，`trg_q_no_reopen` 冻结不可重开**）；**`inconclusive` 是非终态**——`mark_inconclusive` 置 `active → inconclusive` + `visit_count+1`，inconclusive 与 open **一样可被调度器重选**（重选时 `inconclusive → active`）。`dead_end` 关闭须带 decision。
- **调度可见性**：一个 question 可被选中 ⟺ `status ∈ {open, inconclusive}` **且无 pending `question_dep`**（pending dep → 不可选、不开 cycle，对应 §2.3 dependency_wait 注；`blocked` dep 不阻塞调度，语义见 §4.2.4）。`inconclusive` 问题对 **attack** 重选还须 `visit_count` 未达 `max_inconclusive_per_question`（附录 C）——**到限后该问题对 attack 不可选，仅可作为 decompose / propose_prune 的对象**（强制换路的机械落点；`persist_selection` 的「attack 但目标不可调度 → 拒」判据随之覆盖此项）。

**4.2.2 对象生命周期（池侧八事件）。**

| # | 事件 | 概念 | DB 动作 | 文件动作 |
|---|---|---|---|---|
| ① | 立项 | 结构变→新 baseline | `gate_claim_baseline`(I5)→baseline `planned`；claim variant `planned`；写 build_target(build) | — |
| ② | 构建+训练+出厂评估 | 训练产 checkpoint(s)→出厂评估(source=factory) | run(build)→checkpoint(s)；evaluation+attempt+metric_result(I2)；`gate_register_baseline`(I4)→`legal` | **复制非剪切**入池；`checkpoints/` + `evaluations/<eval0>/attempts/1/` |
| ③ | 引用 | 某 evaluation 指标作证据 | EVIDENCE(question→evaluation) | 只读 |
| ④ | 加变体 | 改训练设置→新变体（exec） | claim variant；run(exec)→新 checkpoint(s)；evaluation+attempt+metric_result | `variants/<新key>/` |
| ⑤ | 升级评估协议 | 不动训练，拿 checkpoint 重评(source=protocol_upgrade) | 新 evaluation(同变体)+attempt+metric_result（免 run） | 同变体 `evaluations/<eval1>/attempts/1/` 追加 |
| ⑥ | 复用 | 同变体同评估协议已有成功 evaluation | 测量索引 (variant_id,protocol_id,protocol_ver) 命中→引用，零新评估 | 只读 |
| ⑦ | 派生 baseline | 结构变→新 baseline(parent 指原) | 新 baseline `parent_id`=原；走 ② | 新 `baselines/<b2>/` |
| ⑧ | 弃用 | deprecated（证据保留） | baseline/variant `legal`→`deprecated`（只标记） | 不动 |

贯穿不变量映射：I5 占坑①· I4 注册②· I2 测量履约②⑤· I1 协议场景不可变⑤· append-only ⑤⑧。

> **口径说明（eval 审计载体）**：免训练再评估（target_kind=eval）**不建 run 行**（`run.kind` 仅 {build,exec,import}，eval 无 run）；评估的执行审计事实（env_hash/commit_hash/transcript/watchdog/失败类型/重试/成本）落 **`evaluation_attempt`**——出厂评估与免训练 eval **同构**（都写 evaluation + ≥1 attempt，仅 build/exec/import 额外写 run）。同一 evaluation 失败重试 = 追加 attempt；成功 attempt 经 `canonical_attempt_id` 标定为复用基准。§3.1.1 契约、附录 A DDL 状态机一致。

**4.2.3 失败语义矩阵（轮次正常收尾 vs cycle 失败）。** 区分两类，防把"研究失败"误判成"系统失败"：

| 情况 | cycle.status | 问题/动作 |
|---|---|---|
| idea 全候选不合格 / plan 评审两轮不过 / bundle 关键目标失败 / engineering_blocked / **`gate_close_question` 业务拒且重答（≤2）用尽**（证据不合法 = 证据不足，§3.5.2 既有路径） | **`done`**（研究轮正常收尾） | Qn → `inconclusive`(visit+1，非终态可重调度)；写失败卡 + DECISION；不入研究证据 |
| reasoning 产物**结构**非法（schema / 引用完整性，`artifact_parse` ≤2 用尽） | **`failed`** | 等下一轮或人工；**Qn 回 open（StateStore 释放 active→open、不增 visit——系统失败非研究尝试）** |
| 人类 abort_cycle / 进程异常不可恢复 | **`aborted`** | 问题回 open（StateStore 释放 active→open、不增 visit，同上） |

只有后两类才是 `cycle.status∈{failed,aborted}`；前一类一律 `done`。`Advancer` 据此推进，**不把 idea/plan 失败当作 cycle 失败**。

**4.2.4 状态迁移写入（StateStore，同一写库服务）。** 编排器对状态的写入也经**同一** SQLite 写连接与触发器（非 Codex 产物，由 reasoning `selection`/人类 `directive` 驱动）；函数即接口契约的 `StateStore`：

| 写函数 | 作用 | 拒绝/前置判据 |
|---|---|---|
| `set_route` | 落本轮 `cycle.route`（Advancer 派生，§2.3） | route ∉ 7 形态；cycle 已 done |
| `persist_selection` | 落 `cycle.next_question_id/next_intent`（attack/decompose ⇒ `next_question_id` 非空且可调度；**terminate ⇒ `next_question_id` 必为 NULL** = 持久停机标志）；同步把 `selection.scores[]` 写回对应 `question.score / est_cost`（该两列的唯一维护点） | next_intent ∉ 枚举；attack/decompose 但 `next_question_id` 空或不可调度；**terminate 但 `next_question_id` 非空** |
| `apply_tree_ops` | 写树（攻坚轮尾与 reasoning-only 轮均可；**op 封闭词表，共七个，`tree_ops.json` ABI 与本表一字一致**）：**`create_root`**（bootstrap 建首题）· **`add_children`**（decompose：写子问题 + `decompose_count++`；**同一事务：父问题 `active→open` 释放**[与 dependency_wait 释放同构：等待非尝试、不增 visit] **+ 对每个新子问题写 `question_dep(dep_type=question, pending)`**——子问题 answered / refuted 经 `resolve_deps` 逐条 satisfied，**全部 satisfied 后父问题回 open 可调度集**，聚合轮走 attack-intent → plan(targets=[]) → reuse_only、以 child_answer 证据关闭[§2.3 / §3.3.1]）· **`spawn_question`**（新问题；kind ∈ {diagnosis, followup, revalidate, import_reference, goal_retarget} → `question.source` 映射 {agent, agent, revalidate, agent, goal_amend}；**挂点规则**：诊断 / 后续题 parent = 触发它的问题，revalidate 题 parent = 被回看问题——closed 节点下允许**新增**子节点，禁止的是改既有节点 `parent_id`[触发器]；goal_retarget 建新 root（parent=NULL，goal_amend 轮专用）；受树规模护栏）· **`mark_answer_applicability`**（对既有 answer 写 / 更新**当前 goal_ver** 的 applicability 行，语义见 §4.6.4；历史留痕写 `DECISION(type=answer_review)`）· **`propose_prune`**（agent 剪枝：先写 `decision(type=prune_branch, actor=agent)` 再置 dead_end——`trg_q_deadend` 只验该 decision 存在、不限 actor；人类 `prune_branch` directive 路径照旧）· **`amend_goal`**（goal_amend 轮专用：INSERT goal 新版本 + 全部 open[含 inconclusive]问题 `goal_ver` 原地迁移 + 按新版本重打分，§4.6.4）· **`seed_applicability_audit`**（goal_amend 轮专用：对可能受新根谓词影响的 closed 结论批量建 `pending` applicability 行，受 `max_closed_revalidate_per_cycle`，§4.6.4） | op ∉ 上述七 op 词表；`amend_goal` / `seed_applicability_audit` 出现在非 goal_amend 轮；spawn 超树规模护栏；改 closed 节点树结构（`parent_id` 不可改触发器/防环）；本 cycle 内 `mark_answer_applicability` 次数超 `max_reviews_per_cycle`（附录 C answer_review）；`mark_answer_applicability` 置 needs_revalidation / contradicted 时，spawned_question_id 未指向「`source='revalidate'` 且 parent = 被回看 answer 所属 question」的问题（同批 spawn_question 或既有均可） |
| `mark_inconclusive` | Qn→`inconclusive`、`visit_count+1`（研究轮正常收尾；非终态、可重调度） | Qn 非 active |
| `activate_question` | 选中问题置 active | 问题不可调度（有 pending dep） |
| `record_question_dep` / `resolve_deps` | 写/解依赖（**plan 本轮新写未满足 dep → 派生 `dependency_wait`、同事务把 Qn `active→open` 释放**[等待非尝试、不增 visit]；`baseline→legal` / **依赖问题产生 answer（answered 或 refuted）**时标 satisfied 解锁、问题回 open 集可重选；依赖问题 `dead_end` 不自动满足——下轮 reasoning/plan 写 `decision(blocked_by_dead_dep)` → 改依赖 / prune / 重 plan，非死锁）。**`status='blocked'` 语义收编（硬）**：dep 经裁决豁免 / 阻断记录——须先写对应 DECISION（如 `blocked_by_dead_dep` 后的「改依赖」）再置 blocked；调度排除只看 **pending**（§4.2.1），blocked 不再阻塞调度（即 dead_end 依赖的机械出口：置 blocked + decision，父问题恢复可调度或改走 prune / 重 plan） | 自依赖（DB CHECK 已封）；dep 目标不存在 |
| `consume_directive` | 消费人类 directive（goal_amend/abort 等），写 DECISION | directive 已消费；须回显确认的 directive（硬指令且源自人机消息）其 `payload_json.confirmed ≠ true`（未确认不得消费；确认流水见 §4.6.2） |

> 与 §4.1.4 事实注册**共用事务边界与触发器**——故 §4.1.1 "唯一写库服务"成立；二者区别只在：§4.1.4 校验 Codex 阶段产物，§4.2.4 落编排器状态迁移。

**4.2.5 阶段级原子提交（崩溃不留半写）。** 一个阶段的多产物在**单一事务**内提交，幂等键 = `(cycle_id, stage, target_id?)`（落 `phase_commit` 表，UNIQUE 幂等约束防重复提交；kill-9 重启**同键且 `artifact_hash` 相同才跳过、不同即拒绝**——防 staging 被改写后误判「已提交」；约束表达式见附录 A），编排器经 `commit_phase(stage, cycle_id, target_id?, artifacts)` 协调：
- **reasoning 轮尾**：`answer+evidence → question.status(answered/refuted) → apply_tree_ops → persist_selection → mark_cycle_done` **同一事务**（§3.5.4 (a)）；任一步失败整体回滚，下次 advance 从本阶段幂等重做。**杜绝"问题已关闭但 selection 未落库"半写。** 提交后的 views/Git/通知是 outbox 副作用（§3.5.4 (b) / §4.3）。
- **bundle 逐目标（两段提交）**：**(i) 执行事实提交**——随发生、各自短事务入账，限定为 `gate_start_run`（开训即落 running，§4.1.3 续训）、`gate_finish_run(success/failed)`+checkpoint 登记、**run-owned** 的 `execution_log`/`execution_observation`、执行失败的 `gate_start/finish_attempt(failed)` 及其 attempt-owned log（与《第二部分》§6.13(1)「长操作绝不持写事务」一致）；**成功评估的 log/观测在本段不入库**（`execution_log` 恰一 owner、成功 attempt 尚不存在），先作 staging ref+hash 进结果评审 manifest（§4.1.4 附注）。**(ii) 测量注册提交**——结果评审通过后**单事务**完成 `evaluation + attempt(success) + metric_result + attempt-owned execution_log/observation 补登 + gate_register_* + gate_finish_build_target(complete)`。评审否决 → 第 (ii) 段不发生（run(success)+checkpoint 保留，target `failed(review_failed)`）。**幂等**：第 (i) 段各命令用 WriteDaemon `gate_commit:<gate_fn>` 幂等键 `(cycle,stage,target,artifact_hash)`（§6.13(1)）；`phase_commit(cycle,stage,target)` 的语义 = 每 target 的**注册段（第 ii 段）**提交，唯一键不撞。**目标间不共事务**（`bundle_cursor` 落库分界，崩溃从 cursor 续）。
- **plan（出 targets）**：`gate_new_protocol + 占坑(claim) + build_target 队列 + build_target_required_metric` 单事务。
- **plan（dependency_wait：本轮新写未满足 dep）**：`record_question_dep + set_route(dependency_wait) + Qn active→open（释放、不增 visit）+ mark_cycle_done` **同一事务**；dep 满足前 Qn 因 pending dep 不可调度，满足后回 open 集重选。**import deferred 场景**另含 `external_import(selected_for_materialization) + baseline(planned) 占位 + question_dep` 同一 `phase_commit`（防半写）。
- **decompose（reasoning-only 轮尾）**：`add_children(子问题批) + 父问题 active→open 释放（不增 visit）+ 逐子问题 question_dep(pending) + DECISION(decompose) + persist_selection + mark_cycle_done` **同一事务**（杜绝「子问题已写但父未释放 / dep 未写」半写；释放语义与 dependency_wait 条目同构）。

### 4.3 审计追踪、运行日志与决策账本（三层分清）

三类记录语义不同、**严格分层、不可混用**：

**4.3.1 运行证据层：execution_log / execution_observation（issue ①）。**
- `execution_log`：训 / 评**产物**（原始日志 + 曲线 / event / csv 等）/ smoke / stderr **raw log 的 ref + hash**（冷数据，按 ref 经 ctx-fetch 深潜，§3.6.2 第 4 级）。
- `execution_observation`：结构化观测（nan / 发散 / oom / warning / retry / last_loss / loss_trend / wall_clock），**仅确定性 parser 写**；codex 摘要只存 `digest_ref + digest_hash`、不得冒充观测事实。
- **铁律（raw 内容 vs 派生位）**：raw log / 训练评估产物 / 观测**内容**永不作正向 evidence / metric_result / gate 判据（I3 不变，§3.1.2）；但 parser 据 `execution_observation`（nan / divergence / loss_trend='nan' 等）+ policy 阈值**确定性派生**的质量谓词 `parser_result_suspect`（**非存储列、可复算**）**可作过滤**：挡复用（§4.1.5）、挡关问（`gate_close_question` 拒存疑 attempt 作证据）——它**不是 evidence、不支持结论**，只阻止用坏测量。

**4.3.2 决策账本层：DECISION（语义决策，append-only）。**
- **写入点**（`actor ∈ {agent, gate, judge, human, orchestrator}`，§1.2.3 / 附录 A）：gate 拒绝（actor=gate, type=reject）、judge 审计评分（actor=judge）、Codex 阶段裁决 / 选题（**actor=agent**，type 标 idea/plan/reasoning 子类）、编排器状态决策（actor=orchestrator）、人类 directive 消费（**actor=human**，经 directive、**不直接 FK `interaction_message`**——provenance 经 directive 间接回溯）。
- **写入路径 + 幂等**：与阶段产物**同一 `phase_commit` 事务**（§4.2.5），幂等键随 `(cycle_id, stage, …)`；append-only（附录 A 的 UPDATE/DELETE 禁触发器）。`decision.type` 为自由文本、不需扩枚举。
- **边界（P1/P5）**：`decision` **只记研究决策**——人机 query / reply / ACK **不写 decision**（走 `interaction_*` 自成审计流，§4.6）；软指令系统可有理由地不从、但须在 decision 写明理由。

**4.3.3 成本账本层：LEDGER（预算台账）。**
- 每次 Runner 调用与每个 RUN 的消耗（tokens / 时长 / wall-clock / 货币）记入 `ledger`，按轮聚合到 `cycle.cost_total`。
- LEDGER 是 **DB 结构化账本**、可由 outbox **幂等补写**（§3.5.4 (b)），与 Git / 通知等不可回滚副作用**不同桶**。
- 三处消费：① 采集四元打分的成本项 `cost_norm`；② 单轮预算路由 `B(t)`（§4.4）；③ 全局预算耗尽判停（终止判据②，§4.4）。

**4.3.4 审计回放（P6）。** 上述三层 + `runner_call`（每次 Runner 调用审计）+ 内容寻址快照（检索 / import 选择 / wildidea engine 上下文）**全 append-only**；给定 `policy_hash` 与冻结输入，**回放即重算同一确定性决策**。独立审计**只消费、不改写**真相。

### 4.4 运行时：编排器、预算、恢复与终止

**4.4.1 编排器与 Runner。** 编排器是确定性循环驱动，**从不推理**；它通过窄接口 `run_task` 调用 Codex Runner 适配器（无状态工人，运行时可替换）。运行形态推荐 cron / 循环守护 + `advance(cycle)` 步进：每次唤醒把轮次状态机推进一格 → 落库 → 退出（最笨但与幂等恢复天然契合，可单步调试任意阶段）。`Advancer` 据失败语义（§4.2.3）推进，不把 idea/plan 失败当 cycle 失败。**步进前置检查**：存在未消费的 `pause` directive，或存在 `interaction_request(status='pending')`（文件请求全局等待，§4.6.8）→ 本次不发起新研究 Runner 调用、不推进阶段（人机服务照常，线程隔离 §4.6.2）。

**4.4.2 会话双模式 A/B（M6 实测定默认）。** Codex runtime 是一次性调用、自身不持跨调用状态；连续性完全由应用层在**每个 turn 重建上下文**实现（上下文包 + 中文交接摘要）——这是 P1/P3 的落地：状态在库不在会话。
- **模式 A（一 turn 一阶段）**：一次 Codex 调用只推进一个阶段，阶段边界由编排器控制。粒度细、最易恢复、最易审计。
- **模式 B（一 turn 跨多阶段）**：一次调用内 Codex 可连跑多个阶段、自己决定何时停（"像人一样累了就歇"），turn 内即时落库做检查点。吞吐高、上下文连续性好。
- **共用不变式**：无论 A/B，任何 turn 在任意点终止，下一个 turn 都能凭"上下文包 + 中文交接摘要"无缝续上；两模式只是 turn↔阶段映射粒度不同，恢复保证一致。借鉴 DeepScientist 无状态 Runner 与每-turn 重建机制。

**4.4.3 watchdog。** 每次 Runner 调用带 wall-clock 上限（按任务类型给值，如探针级 2h / 全量级默认 24h），以 transcript 文件 mtime 为**基础心跳**（综合判活信号组合——pid / 结构化心跳 / 资源活性 / 阶段 deadline——见《第二部分》§6.7）；超时即终止会话、写 `RUN(failed, timeout)` 或 target 失败，按重试策略（smoke 修复受预算+watchdog、无固定次数上限见 §3.4.2 / 产物解析 ≤2 / plan 评审 ≤2 / bundle 双评审各 ≤3，附录 C `flow.retry`）处理。连续同型失败超上限的**失败归属与 §4.2.3 一致**：**训练 / 评估 / run timeout → 该 target `failed` 或 `engineering_blocked`**、轮尾正常收尾（`cycle=done` + Qn `inconclusive`）；**仅 orchestrator / 契约 / reasoning 产物非法才 `cycle.failed`**——**绝不无限重试**，超上限 enqueue 通知 outbox。

**4.4.4 预算路由 B(t)。** 单轮预算 `B(t)` 初值≈廉价探针量级，每 m 轮翻倍封顶 `B_max`（早期自然逼出廉价探针）；`selection` 选中问题 `est_cost > B(t)` ⇒ 走 decompose（软约束，执行点 = reasoning R3 提示词（《第二部分》§6.4）、无门禁拦截；§2.3）。成本记账（LEDGER）见 §4.3.3、旋钮见 §4.7。

**4.4.5 恢复。** 阶段边界即检查点（P6）：半成品只写 staging 目录、完成后原子改名；任意时刻 kill -9，重启读在途 CYCLE 的状态字段即从该阶段续跑。验收（恢复性里程碑）：任意阶段杀进程，重启续跑的终库状态与不杀一致。

**4.4.6 终止三判据 τ。** 任一满足即出环全局停机：① 全部 open 问题分数低于 τ 连续若干轮；② 全局预算耗尽；③ 目标谓词满足（reasoning 判定 + 人类确认）。停机后问题树 + baseline 池 + 视图与决策账即最终可复查资产。停机由 `selection.intent=terminate`（`next_question_id=NULL` 持久标志，§4.2.4）落定。

### 4.5 上下文与资产消费（运行时）

> 运行时如何把 DB 真相**编译**成 Codex 输入、用**卡片 / 索引**做按需召回。文件布局 / md 生命周期 / 入库三段缝合是持久化结构、见 §5。

**4.5.1 Context Compiler（上下文编译器）。** 编排器侧确定性组件，把 DB 真相编译成每阶段 Codex 输入（`context_pack`），是"聚焦本轮 + 按需召回"的执行者：
- **分区预算编译**：每阶段输入 = **固定锚**（任务关键集必含、不截断，§3.1.1）+ **检索区**（按 policy 配方召回、有额度），而非全量塞入——长程不漂移、单轮延迟短的关键。
- **观测摘要渲染**：从 `execution_observation` 渲染本轮运行观测摘要进 reasoning 锚点（不塞全量 log，§3.1.2）。
- **每-turn 重建 + 中文交接**：Codex 无状态，编译器每 turn 重建上下文包 + 中文交接摘要（§4.4.2）；冷数据按 ref 经 ctx-fetch 深潜（§3.6.2 第 4 级）。
- **卡片为投影单元**：编译器从卡片（§4.5.2）与召回索引（§4.5.3）取定额 md 片段拼装，不直接读大文件。
- **applicability 徽标（硬；编译器确定性规则）**：任何呈现已关闭结论的面——问题卡、子树摘要卡、「相关已关闭结论 / 相似结论」召回块、status_card、plan 的 reuse_evidence——**必须 join 该 answer 当前 goal_ver 的 `answer_applicability` 行**并渲染**单行**徽标，**六枚举全渲染**（`pending` / `blocked` / `still_applicable` / `needs_revalidation→QN(状态)` / `contradicted` / `obsolete`）；无行 = 无徽标、不占额度。

**4.5.2 卡片体系（物化在 DB）。** 卡片是"为上下文供给设计的定额预算 md 片段"，全部**物化在 DB `card` 表**（摘要存 `card_md` 字段），不落独立文件。FTS / 嵌入索引建在卡片正文上，门禁在同一事务刷新卡片（携带源内容哈希 `src_hash`，落后于真相可机械检出并重建）。

| 卡片 | 额度 | 用途 / 触发刷新 |
|---|---|---|
| 问题卡 | ≤200 tok | 树上一个节点；节点字段变更、或其 answer 的 applicability 行写入 / 更新时刷新 |
| 子树摘要卡 | ≤400 tok | 树上一个**面**；后代关闭或后代 applicability 变更沿祖先链上传刷新（深度由 `subtree_card_depth` 控制，**默认 1、宽度全部**） |
| 方法族卡 | ≤300 tok | 池初筛入口 |
| 基线卡 | ≤250 tok | 池中筛；含变体矩阵 |
| 变体卡 | ≤150 tok | 池精确定位；**含各 evaluation 摘要** + 反向链接 |
| 失败卡 | ≤150 tok | RUN 进 failed 时生成 |
| 协议卡 | ≤150 tok | 新协议登记时生成 |

> 物化（materialization）= 把"本该现算的摘要"提前算好、以行的形式存进 DB，使召回 O(1) 命中、并能在卡片正文上直接建全文 / 向量索引。

**4.5.3 召回与池索引（构建 / 查询 / 失效）。** 召回流程（渐进四级）在 §3.6.2；本节是其**索引机制**：
- **规格索引**：`canonical_key` 唯一 + `baseline_tag`（facet）+ `parent_id`（方法族树）。
- **测量索引（复用判定核心）**：`(variant_id, protocol_id, protocol_ver)` 命中成功 evaluation → **O(1)**（§4.1.5 selector 的索引基础）。
- **语义 / 词法索引**：FTS + 嵌入建在**卡片正文**上（§4.5.2）。
- **反向链接（变体级）**：`born_question`（一对一权威：变体为哪个问题而生）/ `used_by_questions`（从 EVIDENCE 反查派生、物化进变体卡）；补充属性 `baseline.capability_summary` / `variant.result_summary` / `env_hash`。
- **失效与重建**：门禁在写库同一事务刷新相关卡片与索引；卡片带 `src_hash`，落后真相可机械检出并重建（P6）。
- **tag 策略**：tag 挂 **baseline 级**（方法族 / 能力维度；任务 / 数据集维度走 protocol，不走 tag）。

### 4.6 人机入站与消费（issue ④）

**4.6.1 三通道。**
- **web 只读仪表盘**：tree.md / pool.md / goal.md / digest.md 渲染面板，只看不改。
- **QQ bot**：推送（轮失败 / engineering_blocked / 每 K 轮摘要 + 文件请求事件，§4.6.6）+ 接收自然语言。
- **自然语言 → 三分类**：NL 解析 skill 把人话**保守三分类**为 query（问现状）/ directive（改状态）/ note（软注解）（低置信不强分，另出 `unclear`，§4.6.2）——directive 硬指令**回显确认**后生效、软指令入队；query 走只读应答器即时回话（§4.6.2）。

> 借鉴 DeepScientist 工程机制（connector / 异步消息、单一出站网关、入站意图分类、线程隔离）实现，**不抄其 anchor/prompt 主导控制哲学**。

**4.6.2 统一入站 + 保守三分类 + 只读应答器（issue ④，参考 DeepScientist）。** 人主要经 QQ / web 发消息（问现状 / 给目标 / 下指令），系统必须**及时回应**，且**很多消息只是问现状、不改运行**。**所有**人类输入（含 web 控件点按）先落一条 `interaction_message`（raw 不可变 + `idempotency_key`；NL 消息 raw=原文、控件 raw=结构化 payload、`connector` 标 `qq`/`web`/`web_control`）——**唯一权威入站记录**（durable JSONL 信箱只作 connector 临时缓冲、**不作权威队列**，护 P1），再做**保守分类**（`interaction_classification`，每消息恰一；**三种业务意图 + `unclear` 低置信出口**，「三分类」指前者）：

| intent | 含义 | 路径 | 时机 |
|---|---|---|---|
| **query** | 问现状，**不改状态** | 只读应答器带外回话 | **即时**（不等阶段边界） |
| **directive** | 改状态（§4.6.4 指令；含控件指令） | 产独立 `directive` 行（`source_interaction_message_id` 回指本 message）→ 门禁消费 | 按 §4.6.4 |
| **note** | 软注解 | directive(note, 软) | 下一轮 reasoning 开头 |
| **unclear** | 低置信、意图未定（三种业务意图之外的**暂态出口**） | 回显请人确认，**不自动答、不改状态、不产 directive**（DDL：`intent='unclear'` 时 `directive_id` 必空）；后续确认消息按新消息入站重新分类 | 即时回显 |

- **保守铁律 + `continue` 特例**：任何**可能改状态**的语句一律走 directive / 回显确认；只有纯状态查询走 query。**「继续 / 接着跑」单列**：系统在跑 → 即时 ACK「已在继续，当前快照 cycle N」（**不产状态变更 directive**）；系统已暂停 → 作 `resume` directive 经门禁。如此既不把催问变成待确认指令、又不误执行。
- **query 只读应答器（带外、不过门禁、不改状态）**：跑在确定性 advance 循环**之外**（DeepScientist 式线程隔离，研究循环不被人机 IO 阻塞），用**独立只读连接**（SQLite `mode=ro` + authorizer 禁 INSERT/UPDATE/DELETE/DDL/ATTACH）读**发布快照点**——advance 在阶段边界**原子发布**的 `status_card`（物化状态卡：tree/pool/goal/digest + cycle/route/预算）；回答须**区分「上次完成快照(`snapshot_cycle`)」与「当前正在执行(runner heartbeat)」**，不读「逻辑半完成」的已提交片段、不读 md 当真相。
- **中介线程（长在线只读 Codex 会话）与应答硬边界**：解答与传话由一个**可长在线的中介会话**承担——只负责回答 query、双向传递消息、并把用户请求**修正与润色**为规范化表述；每次应答仍各绑一条 `runner_call.phase=interaction_query`。**中介线程的唯一持久状态在 `interaction_*` 表（硬）**：会话可随时终止重建，重建输入 = 最近发布 status_card + 同 `conversation_id` 最近 N 条已消毒入站 / 出站（N 为 policy 旋钮）——多轮指代由此续接，会话只是缓存、P1/P3 不破。**润色不改 raw、落库时序固定（硬）**：原文原样落 `interaction_message`（不可变）；分类为 directive 时**先建 `directive(status=pending)`、`payload_json` 携润色稿 + 润色 runner provenance**（`trg_iclass_directive_prov` 要求分类行插入时 directive 已存在并回指本 message，故 pending 先行是唯一 DDL 兼容时序），**硬指令回显确认展示润色稿**——用户确认的是润色后的语义；**确认不过 → directive 置 `rejected`（不消费）**。**确认的机械落点**：确认消息经分类后由 interaction daemon（经 WriteDaemon 短命令）置该 directive `payload_json.confirmed=true`（directive 行本可迁移状态、非 append-only，DDL 兼容）；`consume_directive` 拒未确认硬指令（§4.2.4）。其余照旧：中介**只拿状态卡文本 + 已分类消毒摘要**（无 DB 凭据、不拿 raw 对话，防注入），**写 `interaction_reply` 的主体是 interaction daemon 单写队列、不是 Codex**；回复入库前过 **grounding 校验**（非门禁）：不得声称状态卡外的事实、不得宣称状态变更已执行、不得引 log/interaction 作 evidence、**不得自行生成 directive**（分类仍由三分类步独立完成）；不过则**退模板渲染**。
- **及时性 SLA（v1）**：connector 收到入站并落 `interaction_message` 后即发 ACK（SQLite 暂不可写则先发「已收到未入账」临时 ACK、后补正式）；query 基于最近发布快照**秒级**回答；**directive 不承诺抢占**，只承诺入账 + 回显生效时机。抢占（quiet-interrupt）推迟，v1 不让人机 IO 抢占执行阶段。
- **不污染账本（P1）**：query / reply / ACK **不写 `decision`**（decision 只记研究决策，§4.3.2）；人机往来全在 `interaction_*` append-only 表、自成审计流。directive 仍同记 DECISION 账（§4.6.3）。

**4.6.3 人不直接改库（P5）。** **改状态**的介入一律经 DIRECTIVE 收件箱、门禁在指定时机消费，人与系统**同记一本 DECISION 账**（query 只读、不改状态，故不经 directive、不写 DECISION，§4.6.2）；**decision 只引用 directive / effect、不直接 FK `interaction_message`**——provenance 经 directive 间接回溯，人机原文只在 `interaction_*`。软指令 = 采集打分的加成项，系统可有理由地不从但须在 DECISION 写明理由；硬指令绕过权衡直接生效。

**4.6.4 指令分类与消费时机。**

| 类型 | 指令 | 消费时机 |
|---|---|---|
| 立即生效（硬） | `set_budget` / `pause` / `resume` / `abort_cycle` | 立即 / 阶段边界 |
| 下一轮 reasoning 轮始（软为主） | `inject_question`(软) / `reprioritize`(pin 硬, boost/suppress 软) / `prune_branch`(硬,置 `dead_end` + `decision(type=prune_branch)`；**非 I3 evidence**) / `goal_amend`(硬,创建目标新版本) / `note`(软) | 下一轮 reasoning 开头 |

**适用性审计 = 通用回看机制（answer_applicability；goal_amend 是其批量触发场景）。** 终态问题不可重开（`trg_q_no_reopen`）；后续研究对旧结论的反馈一律走**三步闭环**：① 任意轮尾 reasoning 据本轮证据 / 召回判定某旧 answer 需回看 → `mark_answer_applicability`（§4.2.4）对其写 / 更新**当前 goal_ver** 的 applicability 行（`UNIQUE(answer_id, goal_id, goal_ver)` 使该行即 **latest 判定**、可 UPDATE；历史留痕 `DECISION(type=answer_review)` append-only）；② 置 `needs_revalidation` / `contradicted` 时**必须 spawn `source=revalidate` 新问题**（DDL CHECK 已强制 `spawned_question_id`），回看题按常规 cycle 解决；③ 回看题关闭后，reasoning 把原 answer 的 applicability 更新为终值（`still_applicable` / `contradicted`；范围限定写 `rationale_md`，如「仅 SEED/DEAP 成立」）。**回看不级联作废测量（硬边界）**：applicability 只作用于 answer 的复用与呈现；`metric_result` / evaluation 的复用判定（§4.1.5）与证据有效性不受影响。呈现规则见 §4.5.1（applicability 徽标）、复用把关见 §4.1.4（`gate_close_question` 负向判据）、护栏见附录 C `answer_review` 节（回看每轮上限；spawn 计入 `max_open_questions`）。

**goal_amend 是本机制的批量触发场景：** 创建 GOAL 新版本（旧版不可变）后，**不批量重开已关闭问题**（防树爆炸）：
1. cycle 创建时若有 pending 硬 `goal_amend` → 走 `route='goal_amend'` 的 **reasoning-only 轮**（§2.3）；若 amend 在 bundle 中途到达，本轮轮尾先按旧目标版本收口 Qn，再消费 amend、为下轮重路由。
2. 全部 **open**（含失败后置 `inconclusive` 的可调度问题）**原地 `UPDATE question.goal_ver = 新版本`**（不复制、不新建 root；`born_goal_ver` 保留来源不变），再按新版本重打分。
3. 对**可能影响新根谓词**的 **closed** 结论建 `answer_applicability` 审计项，reasoning 分批判定：`still_applicable`(可复用) / `needs_revalidation`(派生新问题、不重开旧) / `obsolete`(保留但不参与新目标) / `contradicted`(派生反证问题)。**只有派生的新问题吃 `max_open_questions`**；pending 适用性不算 open。
4. 根谓词按 `goal.predicate_json` 版本演化；新版本下新建 root 或 retarget，旧 root answer 不覆盖；answer/evidence 绑产生时 `goal_ver`，跨版本复用须经 `still_applicable`。
5. 护栏：`max_closed_revalidate_per_cycle` / `max_spawn_from_goal_amend` / `max_decompose_depth`；无法派生又无法复用时写 `decision(type='blocked_by_goal_amend')` + 通知人。

**4.6.5 紧急通道。** 原则上人不碰库；确需手术（如数据损坏修复）：先 `pause` → 离线跑带审计输出的迁移脚本 → 操作补记 DECISION → 再 `resume`。例外本身也要留痕。

**4.6.6 人向状态编译与通知（Context Compiler 的镜像）。** 人与 Codex 同为需要「从 DB 真相编译可消化视图」的消费者；本节钉死人向面的**内容与刷新契约**（全部为派生视图契约、零新表，`status_card` 仍不入核心 schema[§5.0]；实现形态见《第二部分》§6.8）：
- **status_card 内容契约（阶段边界原子发布，字段封闭清单）**：`snapshot_cycle` · goal 当前版本摘要 · active question 问题卡 · `cycle.status / route` · **selection intent + 最近一条 selection DECISION 摘要**（使「现在为什么在跑这个问题」可答）· 预算（`B(t)` / 本轮已花 / 全局剩余）· open / inconclusive 计数 · heartbeat ref · **pending 文件请求摘要**（有 pending `interaction_request` 时：request_id / 条目数 / 已等待时长——使「系统为什么停住」可答，§4.6.8）。应答器只许照卡说话（grounding 校验既有）——**卡里没有的事实就是答不出的事实**，扩展回答能力 = 扩展本清单（经修订流程）。
- **live strip（阶段内活性信号；读侧只读、不经任何 LLM）**：heartbeat 年龄（transcript mtime）· `runner_call(phase, status, started_at)` · `bundle_cursor` 进度（当前 target seq / 总数）· watchdog 剩余 · 本轮 ledger 成本。全为既有 DB 列 / 文件属性；与 status_card 分层呈现：**卡 = 上次完成快照，strip = 正在执行**（§4.6.2 的区分落到 UI 契约）。
- **tree / pool 增量**：`views/` 是 Git 仓（§5.2）——树视图逐轮 diff 派生「新增 / 关闭 / 状态变化节点」清单；`question.source=human` 节点高亮（用户输入改变问题树的可见回路）。
- **通知矩阵（事件 → 通道；经 outbox 幂等投递，§3.5.4(b)）**：directive 全生命周期外显——`received`（ACK，既有）/ `classified` / `pending_confirmation`（硬指令回显，**展示润色稿**）/ `pending_effect`（已入队 + 预计消费点，如「当前 bundle target 2/5 结束后的 reasoning 轮始」）/ `applied`（`consumed_cycle` + 效果摘要，如「生成 Q17」）/ `rejected`（软指令不从时**附 DECISION 理由**）/ `superseded`；叠加三类既有推送（轮失败 / engineering_blocked / 每 K 轮摘要）、**文件请求三事件**（`request_pending` 请求发出 / `request_reminder` 周期提醒（间隔见附录 C）/ `request_resolved` 已解决或取消，§4.6.8）与 applicability 变更提示（旧结论被限定 / 反驳时通知）。各事件的通道开关为 policy 旋钮。
- **raw log 尾部（人可看、非证据）**：允许把 raw log 尾部直接文件流展示给人（UI 恒标「运行观测 · 非证据」）；**永不回流中介 / 应答器输入、永不进证据面板**——证据面板只渲染 `answer → evidence → metric_result` 链（§3.1.2 铁律不变，其禁的是证据链与门禁判据、不禁人眼查看）。

**4.6.7 启动输入（用户初始供给契约）。** 系统启动时用户提供什么，唯一定义在此（形态与目录见 §5.2 /《第二部分》§6.3，运行前提清单见《第三部分》§7.5）。启动输入 = 四件套：
1. **研究目标书 `input/goal_brief.md`**：**YAML frontmatter（必含 `predicate_json` 字段，值为合法 JSON 的成功谓词草案）+ 中文正文（研究目标 + 研究说明：背景 / 注意事项 / 资源与数据说明）**。机械校验：编排器初始化时解析 frontmatter——**缺 frontmatter、`predicate_json` 缺失或非法 JSON → 启动失败**（报错退出并指明缺什么，不建 goal、不进 bootstrap）。
2. **研究现状文件夹 `input/corpus/`**：数据集、文献、既有代码与结果等研究现状，**用户初始供给区、对系统整体只读**（挂载即冻结）；系统只引用（DB 记 path+hash，§5.0 缝合不变量）。**其中代码 / 模型要进 baseline 池必须走既有 claim/register 或 import 门禁（§4.1.4 / §3.6.3），不得绕**——现状文件夹不是绕过池门禁的后门。运行期用户补交的文件不进 corpus，落托管追加区 `input/user_provided/`（§4.6.8）。
3. **计算资源声明**：`policy.yaml` 的 `resources` 节（**只放硬件事实**：GPU 数 / 显存 / 磁盘配额，附录 C；单次执行时限**不在此重复定义**、唯一归 `flow.watchdog`）；plan / bundle 经上下文消费，资源相关的自然语言说明写在目标书正文。
4. **policy 参数**：附录 C 全部旋钮**均带默认值**，用户只改想改的（版本入 Git）。

**goal v1 建立路径**：编排器初始化检测无 goal → 解析 `input/goal_brief.md` → 经 WriteDaemon 短命令 `state:create_goal` INSERT goal v1（`text` = 目标正文、`predicate_json` = 谓词草案；`directive_id`/`created_cycle` 为 NULL，DDL 已兼容）+ 写 `DECISION(actor=orchestrator, type=goal_bootstrap, payload 含目标书内容哈希)` → bootstrap 轮 reasoning 建首题（§2.3 规则 1 机制不变）。后续目标演化一律走 `goal_amend`（§4.6.4）。

**4.6.8 文件请求（系统向人请求供给）。** 系统**确实无法自行获取**推进所需资料时（典型：数据集需申请、湿实验产物须用户去做、关键论文全文取不到），向用户发出**聚合请求单**并进入**全局等待**；能自己获取的信息**不得**请求（防滥用机制见下）。对象 = `interaction_request`（表定义见附录 A；对象登记 §1.3.3）：
- **发起**：任一阶段输出 sidecar `resource_request.json`（§3.1.1 表尾注记；schema 见《第二部分》§6.11——`summary_md` 用**易懂语言**说明「期望做什么 / 为何自己获取不到 / 需要你提供什么」，items[] 逐条含 `kind∈{dataset,paper,wet_lab,other}`、期望文件、**已尝试的获取路径 + 失败原因（必填，缺失即 schema 拒——「能自己获取的不得请求」的自证落点）**、`dest_hint`）。编排器经 WriteDaemon 短命令 `interaction_request_create` 落 `interaction_request(pending)`：**幂等键 `(goal_id, request_hash)`**（重放不开多单）；**创建拒绝判据（policy 执行点）**——`interaction_request.enabled=false`、`len(items) > max_items_per_request`、同 goal 历史请求数（pending+resolved，不含 cancelled）≥ `max_requests_per_goal`，任一命中即拒、该缺口按失败观测处理不等待。**聚合纪律**：发出前把当前已知全部缺口合并进一张单；**partial unique index 强制同一 goal 至多一张 pending 单**（连环开单被 DB 拒）。
- **全局等待（v1，只停研究推进）**：pending 单存在 → `Advancer` 不发起新研究 Runner 调用、不推进阶段（§4.4.1 前置检查，与 `pause` directive 同检查点、语义并列；正在跑的 turn 完成后停）；**interaction daemon / query 应答器 / outbox 通知与提醒 / uploads 校验与 resolve·cancel 写入照常运行**（线程隔离 §4.6.2）。resolve / cancel 后自动恢复。**不新增 route、不新增 cycle 状态**；「等待用户供给」与 §4.4.6 终止停机（terminate）、`pause` 指令是三回事。status_card 携 pending 请求摘要使停因可答（§4.6.6）。
- **交付与解决**：通知经 §4.6.6 三事件外显。用户把文件放入 **`uploads/<request_id>/<item_no>/`**（用户上传区），在控制台逐条答复「已提供 / 无法提供」或整单「取消」——答复入站走既有 `interaction_message(web_control)` + 三分类（不新开入站通道）。interaction daemon 校验文件存在 + hash 入账 → **复制并入托管追加区 `input/user_provided/<request_id>/`**（daemon 写、流程层只读；uploads 原件保留审计）→ 一次性写 `resolution_json`（逐条 `{provided: path+hash}` / `{unavailable: reason}`）+ `resolved_message_id`（provenance）→ `status='resolved'`。**取消同样有 provenance**（`cancelled` 须 `resolved_message_id` + `resolution_json={cancelled, reason}`，不存在无审计取消），效果 = 全部条目按 unavailable 处理。恢复后：provided 条目按 `dest_hint` 从托管区引用 / 复制到消费位置；unavailable 条目由推进到该处的阶段按**失败观测**处理（不作证据），轮尾 reasoning 裁决改道 / 剪枝 / inconclusive（§4.2.3 归类不变）。
- **边界（硬）**：用户提供的文件是**输入资产、不是 evidence**——结论仍须经本系统 harness 的 `metric_result`（I3 原样）；请求 / 答复全在 `interaction_*` 审计流，**不写 `decision`**（比照 §4.6.2 不污染账本纪律，请求单自身即审计记录）；`interaction_request` **不在任何 gate 判据输入集**（附录 A 纪律① 显式列名 /《第二部分》§6.13(2) authorizer deny）。旋钮（开关 / 上限 / 提醒间隔）见附录 C `interaction_request` 节；**无自动超时放弃**——全局等待 + 周期提醒，用户可随时 cancel。

## 5 数据与持久化（DB + 文件双管理）

> 数据设计的落地：先定双底座分工不变量（§5.0），再分**文件管理**（§5.A：分工 / 布局 / md 生命周期 / 缝合）与 **DB 管理**（§5.B：对象表 / 关系 / DDL 摘要 / 字段映射），末尾中文落盘（§5.9）。**对象概念边界以 §1.2/§1.3 为准、不变量以 §1.4 为准**，本章只定字段级落库形态；**DDL 全文见附录 A**。

### 5.0 双底座分工不变量

系统是 **DB + 文件双底座 / 双管理**（§1.1.3），但**结构化状态的唯一真相在 SQLite（P1）**：
- **必落 DB（结构化状态唯一真相）**：对象 / 关系 / 状态 / 指标值 / `path+hash` / 审计账本——凡"系统现在处于什么状态"的查询都只问 DB。
- **必落文件（非结构化内容）**：代码 / checkpoint / 数据集 / raw log + 训练评估产物 / md（identity / 报告 / 视图 / 卡片源）——大资产**只引用不复制**（DB 存 `path+hash`）。
- **缝合不变量**：文件经 DB 的 `path + hash + metadata` 索引与校验，hash 失配即检出（P6）。可从 DB 重渲染的（views/ 卡片）可删可重建；真相载体（identity / protocol spec）则**文件是权威正本，DB 侧存其冻结全文快照**（`baseline.identity_doc` / `protocol.scope_spec_json`，供 gate 校验与查询），两侧一致性由 path+hash 缝合校验保证（§5.4）。
- **不冲突 P1**：双底座是**存储分工**、不是双真相——状态真相单一在 DB，文件是被 DB 索引的内容。
- **outbox / status_card 不在核心 schema**：`status_card`（人机发布快照）= advance 在阶段边界原子物化的**派生卡**（可重建，§4.6.2）；通知 / views-Git **outbox** = 实现层幂等队列（《第二部分》），均**不计入核心 DDL**（附录 A）。

### 5.A 文件管理

**5.1 双真相分工与中介。** **文件是 Codex↔DB 的双向中介**（Codex 永不直接碰 DB）：出 = DB → 上下文编译器 → `context_pack/` → Codex；入 = Codex 产物 → 门禁 → DB。
- **大文件只引用不复制**（checkpoint / 数据集，DB 存 path+hash）。
- **变体不复制代码**：变体只存"完整配置 + 只改动的代码文件（overrides/）"，覆盖在 baseline 的 `src/` 上执行，不复制整份源码。
- **connectors 凭据只引用不落明文**（外部 connector 配置只存引用、不入库明文）。

**5.2 文件系统布局。** 目录**扁平**，派生关系（方法族树）只在 DB 的 `parent_id`，不靠目录层级表达；构建现场在轮目录，门禁入库后**复制（非剪切）**进 `baselines/`。

```
baselines/<b-slug-hash8>/
├── identity.md                    ↔ baseline.identity_doc（冻结）
├── src/…                          ↔ baseline.code_ref
└── variants/<variant-key>/
    ├── config.*                   ↔ variant.config_json（训练任务设置）
    ├── overrides/…                ↔ variant.has_overrides（覆盖 src 执行）
    ├── checkpoints/<ckpt_key>/    ↔ checkpoint.path（LOSO: fold0…fold14）
    └── evaluations/<eval-key>/    ↔ evaluation（对照元 = 一个文件夹）
        ├── attempts/<n>/         ↔ evaluation_attempt（每次执行一条；canonical 标基准）
        │   ├── folds/…           # 各折结果（scope=fold）
        │   ├── aggregate.*       # 聚合 / 平均（scope=aggregate）
        │   └── transcript.ref    # 该次执行的 env/transcript 审计
        └── protocol.ref          # 指向 protocols/<name>@<ver>
protocols/<name>@<version>/spec.md ↔ protocol.scope_spec_json（冻结）
questions/<q>/cycles/<id>/         # 轮工作目录
├── context_pack/（输入临时）+ artifacts/（输出产物）+ build/<key>/（构建现场）
├── transcripts/ + handoff-N.md + cycle_report.md
views/                            # DB 投影（tree/pool/goal/digest），Git 仓，每轮渲染+提交（§3.5.4 outbox）
input/                             # 启动输入（§4.6.7）
├── goal_brief.md                  # 研究目标书（YAML frontmatter 含 predicate_json + 中文正文）
├── corpus/                        # 研究现状文件夹（用户初始供给区，系统整体只读，DB 记 path+hash 引用）
└── user_provided/<request_id>/    # 文件请求托管追加区（daemon 写、流程层只读，§4.6.8）
uploads/<request_id>/<item_no>/    # 用户上传区（文件请求交付，校验并入托管区后原件保留审计，§4.6.8）
```
- **一个 evaluation = 一个 `evaluations/<eval-key>/`；其下每次真实执行（重试/复现）= 一个 `attempts/<n>/`**（多折 + 平均落 attempt 内）。评估协议升级（不动训练）→ 同变体下追加评估文件夹，不覆盖。
- **大文件（权重 / 数据集）只引用不复制**；imported baseline 目录与自建一致（`src/` 为 clone 内容）。
- **`views/` 是 Git 仓**：DB 投影、可删可从 DB 重建。

**5.3 md 三类生命周期。**
1. **真相载体**（identity / summary / protocol spec / cycle_report / handoff / 阶段产物 md）：草稿 → 入库 → 转正 → 冻结 / 归档。
2. **DB 投影**（views/ 每轮渲染落文件；**卡片物化在 DB `card` 表、不落独立文件**，§4.5.2）：可删可重建。
3. **临时快照**（`context_pack/` / transcript）：每 turn 产生，**归档供回放**（P6），非长期真相。

**5.4 文件↔DB 缝合（入库三段）。** 草稿（构建现场文件）→ 入库（门禁写 DB + 登记 path+hash）→ 转正（文件并入主干、identity 转权威、刷新 pool.md 与卡片）。
- **path+hash 绑定**：入库即记 `path + content_hash`，门禁校验 hash（§5.0 缝合不变量）。
- **复制非剪切**：构建现场入池用复制（保留现场供审核，问题关闭后归档）。
- **staging 原子改名**：半成品只写 staging 目录、完成后**原子改名**（P6 恢复，§4.4.5）；`context_pack` / transcript 快照归档供回放。
- **铁律 5**：先执行能跑再入池，规整非前置。

```
baseline_tag(baseline_id, tag, PK 两者)             # 召回 facet（方法族/能力；任务/数据集走 protocol）
```

问题树 / 结论 / 账本 / 卡片对象（完整 DDL 见附录 A）：`goal / question / question_dep / idea / cycle / build_target / answer / answer_applicability / evidence / decision / directive / runner_call / ledger / card`。其中 `answer` 独立表（绑 goal_ver），`evidence` 多态（evaluation/child_answer/human/literature），`runner_call` 记每次 Runner 调用审计，`answer_applicability` 承载通用回看机制（goal_amend 为批量触发场景，§4.6.4）。

**v2.3 增量对象（log / import / interaction）**：
- `execution_log / execution_observation`——运行日志 ref 与结构化观测；**内容不直接作 evidence / metric_result / 正向 gate 判据**，仅 parser 派生负向谓词 `parser_result_suspect` 可过滤复用 / 关问（§4.3.1）。`execution_observation.source='codex'` 时事实字段须 NULL（DB CHECK，附录 A）。
- `external_candidate / license_review / external_import`——外部候选不可变发现快照、license append-only 裁定、确定性选择 / 导入事件（含 `candidate_set_hash`/`selection_key`/`policy_hash`，护 I6；§4.1.6）。
- `interaction_message / interaction_classification / interaction_reply`——人机入站 raw（不可变）、三分类、出站回复；query 不污染 decision 账（§4.6）。
- `interaction_request`（v2.4 增）——文件请求单（§4.6.8）：`pending → resolved | cancelled` 封闭迁移、终态须 provenance（`resolved_message_id`）与 `resolution_json`、身份列冻结、**同一 goal 至多一张 pending 单**（partial unique index）；**不在任何 gate 判据输入集**（同纪律①），请求 / 答复不写 decision。

**5.6 对象关系。**

```
baseline 自引用 parent_id（方法族树）；baseline 1─* variant
variant 1─* checkpoint；variant 1─* run（训练）；variant 1─* evaluation（评估）
evaluation 1─* evaluation_attempt（一次真实执行）；evaluation.canonical_attempt_id →某成功 attempt
evaluation_attempt 1─* metric_result；evaluation *─1 protocol
metric_result *─1 checkpoint（fold 哪一折）；metric_result *─1 metric_def
protocol *─* metric_def（经 protocol_metric）；run 1─* checkpoint
```

**变体层（训练设置在 config）与评估层（protocol 被 evaluation 引用）彻底分开——variant 与 protocol 之间没有边。** 评估协议只通过 evaluation 进入对象模型。

**5.7 DDL 摘要、约束映射与索引。** 全文见附录 A（`sqlite3 :memory:` 可重建：**36 表 / 72 触发器 / 29 索引 / 1 视图，EXIT=0**；索引口径含 UNIQUE 自动索引）。约束按不变量分类：
- **I1 / append-only**：goal / protocol / metric_def / protocol_metric / metric_result / checkpoint / answer / evidence / decision / ledger 的 UPDATE/DELETE 禁触发器；run / evaluation_attempt 终态冻结。
- **I2**：`metric_result` metric ∈ `protocol_metric(eval.protocol)` 触发器。
- **I3**：`trg_q_i3`(关问需 valid evidence)、`trg_evidence_child_scope`(child_answer 子树 / satisfied-dep 递归 CTE)、`trg_q_no_reopen`(终态冻结)。
- **I4**：`gate_register_baseline` 合法性链（identity 完备 + smoke + 协议齐 + 复现命令）。
- **I5**：`baseline.canonical_key` UNIQUE + `variant` UNIQUE(baseline_id,variant_key)。
- **I6**：`evaluation.target_set_hash`（INSERT 写入、身份冻结）+ selector 规范化 + 审计列（§4.1.6）。
- **结构**：`question.parent_id` 不可改(防环 / 重挂)、`question_dep` 禁自依赖、`run.build_target_id` 一致性(`trg_run_target_consistent`)、`trg_eval_no_abandon_if_cited` 双守卫、`phase_commit` UNIQUE(cycle,stage,target) 幂等冻结。
- **索引**：测量索引 `(variant_id,protocol_id,protocol_ver)`、`idx_evaluation_protocol_status`、`idx_run_kind_status`、aggregate 部分唯一索引。
- **否定用例**：所有不变量绕过路径均有 sqlite 否定用例覆盖、证明被 DB 拒绝。

```sql
-- I2 履约 + attempt 归属 + 跨变体一致性
CREATE TRIGGER trg_mr_i2_ins BEFORE INSERT ON metric_result
BEGIN
  SELECT CASE WHEN (SELECT evaluation_id FROM evaluation_attempt WHERE id=NEW.evaluation_attempt_id) <> NEW.evaluation_id
    THEN RAISE(ABORT,'metric_result: attempt not under evaluation') END;
  SELECT CASE WHEN NOT EXISTS (SELECT 1 FROM evaluation e JOIN protocol_metric pm
      ON pm.protocol_id=e.protocol_id AND pm.protocol_ver=e.protocol_ver
      WHERE e.id=NEW.evaluation_id AND pm.metric_id=NEW.metric_id AND pm.metric_ver=NEW.metric_ver)
    THEN RAISE(ABORT,'I2: metric not declared by evaluation protocol') END;
  SELECT CASE WHEN NEW.checkpoint_id IS NOT NULL
      AND (SELECT c.variant_id FROM checkpoint c WHERE c.id=NEW.checkpoint_id)
       <> (SELECT e.variant_id FROM evaluation e WHERE e.id=NEW.evaluation_id)
    THEN RAISE(ABORT,'checkpoint 与 evaluation 不属于同一 variant') END;
END;
-- success ⇔ canonical（INSERT+UPDATE 都校验），canonical 必须是本 eval 成功 attempt
CREATE TRIGGER trg_eval_sc_ins BEFORE INSERT ON evaluation
BEGIN
  SELECT CASE WHEN NEW.status='success' AND NEW.canonical_attempt_id IS NULL THEN RAISE(ABORT,'success evaluation 必须有 canonical_attempt') END;
  SELECT CASE WHEN NEW.canonical_attempt_id IS NOT NULL AND NEW.status<>'success' THEN RAISE(ABORT,'canonical 非空时 evaluation 必须 success') END;
  SELECT CASE WHEN NEW.canonical_attempt_id IS NOT NULL AND NOT EXISTS (
      SELECT 1 FROM evaluation_attempt ea WHERE ea.id=NEW.canonical_attempt_id AND ea.evaluation_id=NEW.id AND ea.status='success')
    THEN RAISE(ABORT,'canonical 必须是本 evaluation 的成功 attempt') END;
END;
CREATE TRIGGER trg_eval_sc_upd BEFORE UPDATE ON evaluation
BEGIN
  SELECT CASE WHEN NEW.status='success' AND NEW.canonical_attempt_id IS NULL THEN RAISE(ABORT,'success evaluation 必须有 canonical_attempt') END;
  SELECT CASE WHEN NEW.canonical_attempt_id IS NOT NULL AND NEW.status<>'success' THEN RAISE(ABORT,'canonical 非空时 evaluation 必须 success') END;
  SELECT CASE WHEN NEW.canonical_attempt_id IS NOT NULL AND NOT EXISTS (
      SELECT 1 FROM evaluation_attempt ea WHERE ea.id=NEW.canonical_attempt_id AND ea.evaluation_id=NEW.id AND ea.status='success')
    THEN RAISE(ABORT,'canonical 必须是本 evaluation 的成功 attempt') END;
  SELECT CASE WHEN NEW.variant_id<>OLD.variant_id OR NEW.protocol_id<>OLD.protocol_id OR NEW.protocol_ver<>OLD.protocol_ver
      OR NEW.source<>OLD.source OR NEW.created_cycle<>OLD.created_cycle OR NEW.eval_key<>OLD.eval_key
      OR NEW.target_set_hash<>OLD.target_set_hash
    THEN RAISE(ABORT,'evaluation 身份字段不可变（含 target_set_hash，I6）') END;
  SELECT CASE WHEN OLD.status='success' AND NEW.status NOT IN ('success','abandoned')
    THEN RAISE(ABORT,'success evaluation 不可回退（只可 success/abandoned）') END;
END;

      OR EXISTS (SELECT 1 FROM answer_applicability aa WHERE aa.answer_id=a.id AND aa.goal_id=NEW.goal_id AND aa.goal_ver=NEW.goal_ver AND aa.status='still_applicable')))

CREATE TRIGGER trg_evidence_child_scope BEFORE INSERT ON evidence WHEN NEW.kind='child_answer'
BEGIN
  SELECT CASE WHEN NOT (
    EXISTS (WITH RECURSIVE sub(qid) AS (
              SELECT NEW.question_id
              UNION ALL SELECT q.id FROM question q JOIN sub ON q.parent_id=sub.qid)
            SELECT 1 FROM answer a
            WHERE a.id=NEW.child_answer_id AND a.question_id IN (SELECT qid FROM sub))
    OR EXISTS (SELECT 1 FROM answer a JOIN question_dep qd
                 ON qd.question_id=NEW.question_id AND qd.dep_type='question'
                    AND qd.depends_on_question_id=a.question_id AND qd.status='satisfied'
               WHERE a.id=NEW.child_answer_id)
  ) THEN RAISE(ABORT,'child_answer 证据须来自当前问题子树或 satisfied question_dep') END;
END;

-- 结构纪律（写入纪律见 §4.1）：execution_log/execution_observation 与 interaction_* **不在任何 gate 判据输入集**——

-- ① 执行日志（append-only；owner=run∨attempt 恰一；按 owner 限 log_kind）
CREATE TABLE execution_log (
  id INTEGER PRIMARY KEY,
  run_id INTEGER REFERENCES run(id),
  evaluation_attempt_id INTEGER REFERENCES evaluation_attempt(id),
  cycle_id INTEGER NOT NULL REFERENCES cycle(id),
  log_kind TEXT NOT NULL CHECK (log_kind IN ('train','eval','smoke','stderr','platform','import_clone')),
  ref TEXT NOT NULL, content_hash TEXT NOT NULL, bytes INTEGER CHECK (bytes IS NULL OR bytes >= 0),
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CHECK ((run_id IS NULL) != (evaluation_attempt_id IS NULL))           -- 恰一 owner

CREATE UNIQUE INDEX ux_execlog_run     ON execution_log(run_id, log_kind, content_hash) WHERE run_id IS NOT NULL;
CREATE UNIQUE INDEX ux_execlog_attempt ON execution_log(evaluation_attempt_id, log_kind, content_hash) WHERE evaluation_attempt_id IS NOT NULL;
CREATE TRIGGER trg_execlog_owner BEFORE INSERT ON execution_log
BEGIN
  SELECT CASE WHEN NEW.run_id IS NOT NULL AND (
      NEW.log_kind NOT IN ('train','smoke','stderr','platform','import_clone')
      OR (SELECT cycle_id FROM run WHERE id=NEW.run_id) <> NEW.cycle_id
      OR (NEW.log_kind='train'        AND (SELECT kind FROM run WHERE id=NEW.run_id) NOT IN ('build','exec'))
      OR (NEW.log_kind='import_clone' AND (SELECT kind FROM run WHERE id=NEW.run_id) <> 'import'))
    THEN RAISE(ABORT,'execution_log: run owner 的 log_kind/cycle/kind 不一致') END;
  SELECT CASE WHEN NEW.evaluation_attempt_id IS NOT NULL AND (
      NEW.log_kind NOT IN ('eval','stderr','platform')
      OR (SELECT cycle_id FROM evaluation_attempt WHERE id=NEW.evaluation_attempt_id) <> NEW.cycle_id)
    THEN RAISE(ABORT,'execution_log: attempt owner 的 log_kind/cycle 不一致') END;
END;
CREATE TRIGGER trg_execlog_noupd BEFORE UPDATE ON execution_log BEGIN SELECT RAISE(ABORT,'execution_log append-only'); END;
CREATE TRIGGER trg_execlog_nodel BEFORE DELETE ON execution_log BEGIN SELECT RAISE(ABORT,'execution_log 不可删'); END;

-- ① 执行观测（append-only；FK 溯源到 log；机器事实仅 parser 写，codex 摘要只存 ref+hash，绝不冒充观测事实）

  retry_count INTEGER CHECK (retry_count IS NULL OR retry_count >= 0),

  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  -- codex 摘要不得写任何机器事实/解析列，只准 digest_ref+digest_hash（叙述在被引制品里、不入库当事实，护 P4）

-- 对照 / 审计 + reasoning 可达视图：每条 metric_result 一跳取其评估 / 训练产物 ref（train/eval 产物：原始日志 + 曲线/event/csv 等）。
-- 纪律：属人 / 审计 / 对照 + reasoning 可达族，绝不登记进 gate_input_*；底表含 execution_log → Gate 连接 authorizer
--       既有 deny SELECT execution_log 自动拒之（§6.13(2)）。产物永不作正向 evidence / gate 判据（I3 不变）。
-- group_concat 经内层 ORDER BY rh 稳定展示；本视图不入 hash / 不作 I6 确定性产物。
CREATE VIEW v_metric_result_trajectory AS
SELECT
  mr.id AS metric_result_id, mr.evaluation_attempt_id, mr.scope,
  -- 评估产物：attempt-owned，fold/aggregate 行都直达（同 attempt 共享其评估产物）
  (SELECT group_concat(rh) FROM (
     SELECT el.ref || '@' || el.content_hash AS rh
       FROM execution_log el
      WHERE el.evaluation_attempt_id = mr.evaluation_attempt_id AND el.log_kind = 'eval'
      ORDER BY rh))                                                   AS eval_artifact_refs,
  -- 训练产物：fold 行=自身 checkpoint 的训练 run；aggregate 行=其 attempt 全部 fold checkpoint 的训练 run（去重）。
  -- 无 build/exec 训练 run（produced_by_run NULL）→ JOIN 落空 → NULL（诚实表达）。
  (SELECT group_concat(rh) FROM (
     SELECT DISTINCT el.ref || '@' || el.content_hash AS rh
       FROM metric_result f
       JOIN checkpoint ck    ON ck.id = f.checkpoint_id
       JOIN execution_log el ON el.run_id = ck.produced_by_run AND el.log_kind = 'train'
      WHERE f.scope = 'fold'
        AND ( (mr.scope = 'fold'      AND f.id = mr.id)
           OR (mr.scope = 'aggregate' AND f.evaluation_attempt_id = mr.evaluation_attempt_id) )
      ORDER BY rh))                                                   AS train_artifact_refs
FROM metric_result mr;

-- 纪律同人机表：不在任何 gate 判据输入集（authorizer deny 显式列名，《第二部分》§6.13(2)）；请求/答复不写 decision

  id INTEGER PRIMARY KEY,
  goal_id INTEGER NOT NULL, goal_ver INTEGER NOT NULL,
  cycle_id INTEGER REFERENCES cycle(id), question_id INTEGER REFERENCES question(id),

  status TEXT NOT NULL CHECK (status IN ('pending','resolved','cancelled')),
  summary_md TEXT NOT NULL,                 -- 易懂语言：期望做什么 / 为何自己获取不到 / 需要用户提供什么

  request_hash TEXT NOT NULL CHECK (length(request_hash) > 0),   -- items 内容哈希；创建幂等锚 (goal_id, request_hash)
  resolution_json TEXT,                     -- 终态一次写入：resolved=逐条 {provided: path+hash}|{unavailable: reason}；cancelled={cancelled, reason}
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  resolved_at TEXT,
  resolved_message_id INTEGER REFERENCES interaction_message(id),   -- 用户答复/取消的入站 provenance（终态必填）

  CHECK ((status = 'pending') = (resolution_json IS NULL)),
  CHECK ((status = 'pending') = (resolved_at IS NULL)),
  CHECK ((status = 'pending') = (resolved_message_id IS NULL))
);
-- 「聚合一次性说清」的机械落点：同一 goal 至多一张 pending 单
CREATE UNIQUE INDEX uq_ireq_one_pending ON interaction_request(goal_id) WHERE status='pending';
-- 身份冻结：pending 期只允许一次性迁入终态（status/resolution/resolved_* 同时写），其余列不可改
CREATE TRIGGER trg_ireq_identity_frozen BEFORE UPDATE ON interaction_request
WHEN NEW.goal_id<>OLD.goal_id OR NEW.goal_ver<>OLD.goal_ver OR NEW.cycle_id IS NOT OLD.cycle_id
  OR NEW.question_id IS NOT OLD.question_id OR NEW.stage<>OLD.stage OR NEW.summary_md<>OLD.summary_md
  OR NEW.items_json<>OLD.items_json OR NEW.request_hash<>OLD.request_hash OR NEW.created_at<>OLD.created_at
BEGIN SELECT RAISE(ABORT,'interaction_request 身份列冻结(仅 status/resolution/resolved_* 可一次性迁移)'); END;
CREATE TRIGGER trg_ireq_terminal_frozen BEFORE UPDATE ON interaction_request WHEN OLD.status <> 'pending'
BEGIN SELECT RAISE(ABORT,'interaction_request 终态冻结(resolved/cancelled 不可再改)'); END;
CREATE TRIGGER trg_ireq_nodel BEFORE DELETE ON interaction_request
BEGIN SELECT RAISE(ABORT,'interaction_request 不可删'); END;
```
