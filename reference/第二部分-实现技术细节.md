> 本部分给出**以 Codex 为运行时**的系统「怎么造」：运行时与技术选型、仓库结构、四阶段 skill、MCP 只读工具、资产层（Gate / StateStore / 触发器 / 卡片 / 上下文编译器）、编排器、人机 interaction 服务、外部 import 子系统、桩→真接口契约、产物 schema、policy 旋钮。
> **设计真相唯一在《第一部分》**（对象模型 / 不变量 / DDL）；本部分**引用它、不复述**（引用用「§x.y.z」指《第一部分》对应节）。里程碑顺序与验收见《第三部分》。

## 6 实现技术细节

### 6.1 实现策略概括

**实现策略：流程层先行、资产层占坑、逐层落实。** 先用 skill + system_prompt 把元循环 idea→plan→bundle→reasoning 走通（Codex 当无状态阶段工人），资产层 / 上下文编译器 / 编排器先用**接口桩**（in-memory / 假数据，桩与真实现共用同一签名）顶住；随后逐个里程碑把桩换成真实现。**铁律：占坑是接口桩、不是 prompt 里造假——状态永远在接口（gate / ctx / compiler / recall / state）之后，不在会话里**，否则退回 prompt-led，与本系统 orchestrator + truth-led 的命根相悖。资产层接口契约（两阶段的缝）见 §6.10。

### 6.2 运行时与技术选型

| 关注点 | 选型 | 理由（取舍） |
|---|---|---|
| **智能运行时** | **Codex**（无状态工人，一任务一会话、自身不持跨调用状态）；窄接口 `run_task(system_prompt, skill, context_pack) → Artifact`；M0 实现 = `codex exec` 一次性调用，运行时可替换 | P3：状态在库不在会话；可替换才不被某一模型绑死。连续性由应用层每 turn 重建上下文（上下文包 + 中文交接摘要）实现 |
| **真相存储** | **SQLite（WAL）**：daemon 侧**单一写连接** + 72 触发器（含 v2.3 / v2.4 增量）；`views/`（DB 投影，Git 仓，可重建） | 单机嵌入、零运维；触发器把不变量 + append-only **焊在 DB 层**；WAL 让只读连接（人机查询应答器、召回）与单写互不阻塞 |
| **编排 / 调度** | **Python 确定性编排器**（从不推理）；cron 或循环守护 + `advance(cycle)` 幂等步进；watchdog 以 transcript mtime 为**基础心跳**（综合判活 §6.7） | P6：步进幂等、kill -9 可续跑；「每次唤醒推进一格→落库→退出」最笨但与幂等恢复天然契合 |
| **召回 / 索引** | **FTS5 + 嵌入索引**，建在卡片正文（`card.card_md`）；测量索引 `(variant_id, protocol_id, protocol_ver)` 做 O(1) 复用命中 | 卡片是「定额预算 md 片段」，物化进 DB 才能 O(1) 命中并直接在正文建索引（见《第一部分》§4.5.2 / §3.6.2） |
| **人机通道** | **connector 抽象**（QQ / web / web_control，send/poll/status）+ interaction 服务 + 只读应答器（见 §6.8） | 多平台一套抽象；只读查询走带外只读连接，不阻塞研究循环（见《第一部分》§4.6.2） |
| **落盘语言** | 人读产物 / 提示词全中文；代码标识符 / DB 枚举 / JSON 键英文 | 硬约定，便于人审计与跨轮交接（见《第一部分》§5.9） |

**Codex 的只读纪律（贯穿）**：给 Codex 的 MCP 工具一律只读（§6.5）；Codex **没有 DB 凭据、没有 `views/` 写权限**；产物经文件中转、过三级校验 + 门禁才入库（§6.6）。

### 6.4 流程层：system_prompt + 四阶段 skill

**system_prompt（角色锁定）**：声明 Codex 是**无状态阶段工人**——只处理本 turn 的 context_pack、要什么历史都经 MCP 只读工具取（不得「记住」上一轮事实）、产物只产**合 schema 的 JSON + md 正文**、提交前用 `validate_artifact` 自检、**永不直接碰 DB / views**、跨 turn 经「上下文包 + 中文交接摘要」续接。

**四阶段 skill 通用骨架**（每个 `SKILL.md`）：`触发条件 / 读取(context_pack 四区) / Codex 任务 / 产物 schema(指向 §6.11) / 门禁与写入(指向 §6.6) / 失败语义`。四阶段的**契约与 IO**（输入固定锚 + 输出门禁入库）以《第一部分》§3.1.1 为准；**统一可选 sidecar**：任一阶段确实无法自行获取所需资料时可输出 `resource_request.json`（§6.11；主产物因缺资料缺失但 sidecar 合法 → 不计 artifact_parse 失败、经 `interaction_request_create` 落请求单进入全局等待，恢复后本阶段从检查点重跑——《第一部分》§3.1.1 表尾注记 / §4.6.8）。本节给**实现形态**：

> 独立审计（idea/plan/bundle 各设评审会话，只见产物与上游契约、不见生产过程，评分写 `DECISION(actor=judge)`）：优先在阶段会话内 spawn Codex 子智能体，运行时不支持则回退编排器侧独立 Runner 调用（《第一部分》§3.1.3）。bundle 双评审即此契约的两个实例：评审会话 `runner_call.phase='audit'`、`purpose='bundle_code_review'/'bundle_result_review'`，DECISION payload 与 subject manifest 按《第一部分》§4.1.4 附注由编排器构造。

> **idea_engine_adapter 是唯一壳（护 P1/P3/P6）**：vendored wildidea 的**所有输入、检索、禁词、anchor_pack 只能由上下文编译器 + 只读 MCP 快照提供**，engine **不得自取上下文**（读本地 repo / 历史文件 / 即时网络）；联网查重经只读 MCP、结果入内容寻址快照。**两次 runner_call 独立性可验证**：不同 session / transcript / context_pack / seed / sampling，判官**不见**生成器的自由推理与隐藏上下文。

### 6.5 MCP 只读工具

给 Codex 会话的 MCP 工具**一律只读**（Codex 没有 DB 凭据、没有 `views/` 写权限）：

|---|---|---|
| `ctx-fetch(ref)` | 按 ref 深潜未入包冷数据：identity / evaluation / `src/` / 历史结论 / **raw log + 训练评估产物（`execution_log.ref`）**；预算内换页 | 各阶段（渐进召回第 4 级，《第一部分》§3.6.2） |
| `lit-search(query)` | 论文粗查（只读，结果作内容寻址快照） | idea 新颖性查重；import 发现（论文侧） |
| `repo-search(query)` | GitHub / 代码检索（只读，带 star/maintenance/license/revision 快照） | import 发现（`phase=import_search`，§6.9） |
| `validate_artifact(artifact)` | 产物预检：schema + 引用完整性自查，**不写库** | 各阶段提交前自检 |
| `get_global_status(detail, locale)` / `get_research_map_status` | 渲染**发布快照点**状态卡（tree/pool/goal/digest + cycle/route/预算），只读 | 人机查询应答器（§6.8） |

**预检与提交分离**：`validate_artifact` 的会话内预检**不被信任**——真相侧（编排器事务内）总要**重新**跑三级校验才写库（《第一部分》§4.1.3）。**`ctx-fetch` 取的 raw log / 训练评估产物 只进解释 / 诊断上下文，不进 answer evidence、gate 判据、selection score 的结构输入**（与 §6.13(2) 一致）。

### 6.6 资产层实现：Gate / StateStore / 触发器 / 卡片 / 上下文编译器

**唯一写库服务**：daemon 侧**单一 SQLite 写连接** + 72 触发器恒在。两族写入**共用同一事务边界 + 触发器**——①**事实注册**（`gate_*`，校验 Codex 阶段产物）②**状态迁移**（`StateStore`，编排器据 reasoning `selection` / 人类 `directive`）。「唯一写入口」指唯一**写服务**而非唯一函数；Codex 永不持库凭据。

- **三级校验**（LLM 与真相之间的确定性仲裁）：① JSON schema ② 引用完整性（所引 id 真实存在）③ 业务门禁（不变量 I1–I6；I6 经 gate + selector 否定用例 + `target_set_hash` 审计列）。任一级失败当场拒、记 `DECISION(actor=gate, reject)`，按 policy 重试 ≤2 次仍败升级为阶段失败。
- **`Gate`**：`preview(artifact)`（MCP 只读预检）/ `commit(artifact, cycle_id, stage, target_id?)`（事实注册写库，bundle 逐目标必传 target_id）。门禁函数表（输入 / DB 写入 / 拒绝判据，M1 据此实现）见《第一部分》§4.1.4：`gate_claim/register_baseline`·`gate_claim/register_variant`·`gate_start/finish_run`·`gate_start/finish_attempt`·`gate_*_build_target`·`gate_new_protocol`·`gate_close_question` 等。
- **`gate_input_*` 只读视图（结构护栏，对应《第一部分》附录 A.1 铁律（gate_input 隔离））**：门禁判据只从 `gate_input_*` 视图取数，**该视图集不含** `execution_log` / `execution_observation` / `interaction_*`——日志 / 聊天 / 外部检索永不进门禁；gate 输入快照入账以证明未读它们。
- **`StateStore`**（与 Gate 共用写服务）：`open_or_resume_cycle` / `set_route` / `persist_selection` / `apply_tree_ops` / `mark_cycle_done` / `activate_question` / `mark_inconclusive` / `record_question_dep` / `resolve_deps` / `consume_directive` / `bundle_cursor`（语义与拒绝判据见《第一部分》§4.2.4）。
- **触发器（72）**：不变量 + append-only + 终态冻结 + v2.3 增量（log/import/interaction）+ v2.4 增量（`interaction_request`）全部焊在 DB 层（《第一部分》附录 A）；M1 落地时附**否定用例**逐一证明被 DB 拒绝。
- **卡片物化**：`card` 表（`card_md` + `src_hash`），门禁**同事务**刷新（落后于真相可凭 `src_hash` 机械检出并重建）；FTS5 / 嵌入索引建在 `card_md`。卡片类型与额度见《第一部分》§4.5.2。
- **上下文编译器 `Compiler.render(cycle_id, stage, target_id?)`**：组四区包（① 固定锚不截断 ② 结构邻域 ③ 检索区 top-k ④ 引用区 ref 清单）；**确定性**：同快照 + 同配方 + 同预算 + 同 target → 字节一致。两个 v2.3 渲染职责：reasoning 锚点的**运行观测摘要段**从 `execution_observation` 渲染（不塞全量 log）；人机应答器的 **`status_card`** 由 advance 在阶段边界**原子发布**（发布快照点，§6.8）。
- **阶段级原子提交 `commit_phase(stage, cycle_id, target_id?, artifacts)`**：幂等键落 `phase_commit(cycle,stage,IFNULL(target,-1))` 并记 `artifact_hash`（规范产物集哈希；schema / policy / compiler / runner_call 等溯源哈希各归其账：decision / runner_call / ledger，不进 phase_commit）；kill-9 重启时**同键且同 `artifact_hash` 才跳过，不同（staging 被改写）则拒绝**、不误判「已提交」（《第一部分》§4.2.5）。reasoning 轮尾 `answer+evidence → question.status → apply_tree_ops → persist_selection → mark_cycle_done` **同一事务**（杜绝「问题已关但 selection 未落库」半写）。

### 6.7 编排器 Advancer + watchdog + 预算 + 恢复

- **`Advancer.advance(cycle_id)`**：读 StateStore 把状态机推进一格 → 落库 → 退出；**幂等**（该阶段 artifact / runner_call 已成功则跳过）。**步进前置检查**：未消费 `pause` 或存在 `interaction_request(pending)`（文件请求全局等待，《第一部分》§4.4.1/§4.6.8）→ 不发起新研究 Runner 调用；人机线程照常。运行形态 = cron / 循环守护。
- **`derive_next_route(prev_selection, plan_outcome)`**：据 `next_intent` + plan 落的 `target_kinds` 派生下一轮 `route`（attack 含 build/exec→`attack`；仅 eval→`eval_only`；空且无 blocked→`reuse_only`；blocked（本轮新写 pending dep，**含 import deferred 业务三写入**）→`dependency_wait`；decompose→`decompose`；terminate→停机、本轮 route 不改写）。`Selection`/`Route` 派生规则见《第一部分》§2.3。
- **watchdog**：每 Runner 调用带 wall-clock 上限（按任务类型，如探针 2h / 全量默认 24h），以 transcript mtime + **runner pid/进程组活性 + 结构化心跳 + CPU/GPU/子进程活性 + 阶段 deadline** 综合判活（防长算不写日志被误杀、防卡死刷日志逃逸）；超时终止会话、**确定性写** `RUN(failed, timeout)` 或阶段失败。重试策略：smoke 修复受预算 + watchdog（无固定次数上限）/ 产物解析 ≤2 / plan 评审 ≤2 / bundle 双评审各 ≤3（附录 C `flow.retry`）；连续同型失败超上限 → 轮失败 + 通知人。**绝不无限重试**。
- **预算台账 `ledger`**：每 Runner 调用与每 RUN 的 tokens / 时长 / wall-clock / 货币入账，按轮聚合 `cycle.cost_total`。三处消费：采集成本项；单轮预算 `B(t)`（初值≈廉价探针，每 m 轮翻倍封顶 `B_max`）；全局预算耗尽判停。
- **恢复（P6）**：阶段边界即检查点；半成品只写 staging 目录、完成后原子改名；任意时刻 kill -9，重启读在途 cycle 状态字段即从该阶段续跑。验收（M3）：任意阶段杀进程、重启续跑终库状态与不杀一致。
- **import 的里程碑降级（M1–M3）**：planner 遇「需引入外部 baseline」时，`external_candidate` 发现快照经 `import_register` 短命令登记（§6.13(1)），plan 阶段 phase_commit 落**业务三写入**（`external_import(selected_for_materialization)` **审计状态** + 占位 `baseline(planned)` + `question_dep(dep_type=baseline, pending)`；并与 set_route(dependency_wait)、Qn 释放回 open、mark_cycle_done 同一 phase_commit 事务，《第一部分》§3.6.3/§4.2.5）——问题因 pending dep 不可调度（`import_pending_materialization` 仅为该处境的**描述名、非新增状态**），**不建 `build_target(import)`、不产可执行 target、不卡死循环**（详 §6.9）。

### 6.8 人类控制台与 interaction 服务

实现《第一部分》§4.6 的人机接口；**研究循环与人机 IO 线程隔离**（advance 在自己线程跑，人机在 connector / 应答器线程，互不阻塞）。

- **connector 抽象**（`orchestrator/interaction/connector.py`）：`BaseChannel`(send / poll / status) + `conversation_id ↔ goal/cycle` 绑定（持久化）+ 注册表（`qq` / `web` / `web_control` → channel）。durable inbox jsonl 只作**临时缓冲、非权威队列**（权威入站记录是 `interaction_message`，护 P1）。
- **入站流水**：connector 收消息 → 落 `interaction_message`（raw 不可变 + `idempotency_key`；NL raw=原文、控件 raw=结构化 payload、`connector` 标来源）→ **即时 ACK**（短事务落库后发；写队列暂被长任务占用则先发临时 ACK、**文案明确「已收到、未入账」**，待 `interaction_message` 落库后补正式；长 runner/clone 不持写事务，见 §6.13(1)）→ classifier 保守三分类 → `interaction_classification`（每消息恰一）。
- **classifier**（廉价 NL / 关键词，仿 DeepScientist `classify_turn_intent`）：query（问现状）/ directive（改状态）/ note（软）/ **unclear（低置信暂态：回显请人确认——不自动答、不改状态、不产 directive；确认消息按新消息重新入站分类，《第一部分》§4.6.2；DDL：intent='unclear' 时 directive_id 必空）**。**保守铁律**：可能改状态 → directive / 回显确认。**`continue` 特例**（「继续 / 接着跑」）：系统在跑 → 即时 ACK「已在继续，cycle N」**不产 directive**；已暂停 → `resume` directive。
- **query 路径（中介线程 = 只读应答器，带外）**：`orchestrator/interaction/responder.py` 用**独立只读连接**（SQLite `mode=ro` + authorizer 禁 INSERT/UPDATE/DELETE/DDL/ATTACH）读 advance **原子发布的 `status_card`**（发布快照点），回答**区分「上次完成快照(`snapshot_cycle`)」与「当前正在执行(runner heartbeat)」**。自然语言回复 = **只读 Codex 中介会话**（`phase=interaction_query`，只拿状态卡文本 + 已分类消毒摘要、无 DB 凭据、不拿 raw 对话）→ 过 **grounding 校验**（不得声称状态卡外的事实 / 不得宣称状态变更已执行 / 不得引 log·interaction 作 evidence / 不得自行生成 directive，不过则**退模板渲染**）→ connector 发出 → `interaction_reply` 由 **interaction daemon 单写队列**写（**非 Codex 写**）。**中介会话形态（接口签名不变）**：`Responder.answer(sanitized_query, status_card)` 的 `sanitized_query` 由 interaction daemon 按**会话重建规则**拼装（同 `conversation_id` 最近 N 条已消毒入站/出站 + 本条消毒查询；N 为 policy 旋钮）——中介会话可长在线亦可每次重建，二者**语义等价**（唯一持久状态在 `interaction_*`，§4.6.2）。
- **directive 路径**：分类为 directive → 产独立 `directive` 行（`source_interaction_message_id` 回指本 message，触发器焊死 provenance）→ 门禁按 §4.6.4 消费时机消费（立即 / 阶段边界 / reasoning 轮始）。**润色流水（§4.6.2 时序）**：classifier 判 directive → 中介产**润色稿** → **先建 `directive(status=pending, payload_json=润色稿+润色 runner provenance+confirmed:false, source_interaction_message_id=本消息)`** → 分类行落库（CHECK/触发器满足）→ 硬指令回显确认展示润色稿 → 确认消息落库分类后 daemon 置 `payload_json.confirmed=true`；确认不过置 `rejected`；`consume_directive` 拒未确认硬指令（§4.2.4）。
- **人向编译发布物（§4.6.6 的实现）**：status_card 按 §4.6.6 字段封闭清单渲染（含 pending 文件请求摘要）；live strip 数据源 = `runner_call` / `bundle_cursor` / `ledger` / transcript mtime（只读连接）；通知矩阵经 outbox 幂等投递（事件 = directive 状态迁移 + 三类既有推送 + 文件请求三事件 + applicability 变更）。raw log 尾部：web 直接文件流（只读），恒标「运行观测 · 非证据」，不进中介输入。
- **文件请求流水（《第一部分》§4.6.8 的实现）**：阶段 sidecar 合法 → 编排器经 WriteDaemon `interaction_request_create` 落 pending 单（幂等键 + policy 三拒绝判据，§6.13(1)）→ outbox 发 `request_pending`、按 `remind_interval_h` 发 `request_reminder`；**全局等待期间本节全部服务照常**（线程隔离）。用户答复经既有入站流水（`interaction_message(web_control)` + 三分类）；daemon 校验 `uploads/<request_id>/<item_no>/` 文件存在 + hash → 复制并入 `input/user_provided/<request_id>/` → 一次性写 `resolution_json` + `resolved_message_id` 置 resolved（或 cancelled）→ 发 `request_resolved`，Advancer 恢复。
- **SLA（v1）**：ACK 秒级；query 基于最近发布快照秒级；**directive 不承诺抢占**，只承诺入账 + 回显生效时机（quiet-interrupt 抢占推迟）。
- **不污染账本**：query / reply / ACK **不写 `decision`**；`decision` 只引用 `directive` / effect、不直接 FK `interaction_message`；人机原文只在 `interaction_*`。

### 6.10 接口契约（桩→真，流程层↔资产层的唯一缝）

流程层（skill + system_prompt + 驱动器）只经下列接口读写状态——**状态永远在接口之后、不在会话 / prompt 里**。M0 用桩（in-memory / 假数据），M1+ 换真实现，**签名不变**。约定语言 Python（`Protocol` / ABC）。

```python
class Runner(Protocol):      # M0 起即真（codex exec）
    def run_task(self, *, system_prompt: str, skill: str, context_pack: "ContextPack") -> "Artifact": ...
class Compiler(Protocol):    # 出：DB→context_pack（确定性四区包）
    def render(self, *, cycle_id: str, stage: "Stage", target_id: str | None = None) -> "ContextPack": ...
class Gate(Protocol):        # 三级校验 + 门禁 = 唯一写库入口
    def preview(self, artifact: "Artifact") -> "ValidationResult": ...                       # 只读预检、不写库
    def commit(self, artifact: "Artifact", *, cycle_id: str, stage: "Stage", target_id: str | None = None) -> "CommitResult": ...
class Ctx(Protocol):         # 按 ref 深潜冷数据（MCP 只读）
    def fetch(self, ref: "Ref") -> str: ...
class Recall(Protocol):      # 渐进四级召回
    def query(self, spec: "RecallSpec") -> list["Hit"]: ...
class StateStore(Protocol):  # 状态读写（M1 落 SQLite，单一真相）
    def open_or_resume_cycle(self) -> "Cycle": ...
    def set_route(self, cycle_id, route) -> None: ...
    def persist_selection(self, cycle_id, sel: "Selection") -> None: ...
    def apply_tree_ops(self, cycle_id, ops: "TreeOps") -> None: ...
    def mark_inconclusive(self, question_id) -> None: ...
    def consume_directive(self, directive_id) -> None: ...
    def bundle_cursor(self, cycle_id) -> str | None: ...
    # …（mark_cycle_done / activate_question / record_question_dep / resolve_deps / list_schedulable_questions / create_goal——编排器初始化自 input/goal_brief.md 建 goal v1，《第一部分》§4.6.7）
class Advancer(Protocol):    # M3：推进 + 恢复
    def advance(self, cycle_id) -> "Stage | Literal['done']": ...
    def derive_next_route(self, prev_selection: "Selection", outcome: "PlanOutcome") -> "Route | None": ...
```

`Selection`（reasoning 产物）= `{next_question_id, next_intent ∈ {attack, decompose, terminate}, scores[]}`——**只选下一步、不写 route**；route 由 `Advancer.derive_next_route` 派生。**写入纪律**：`StateStore.*` 与 `Gate.commit` 共用同一 SQLite 写服务 / 事务边界，不得各开写入口。

class ObservationExtractor(Protocol):

class PhaseCommitStore(Protocol): ...   # 幂等键 (cycle,stage,target) + artifact_hash 比对：同→跳过，异→拒绝（§6.6 /《第一部分》§4.2.5）

### 6.13 命根机制化（enforcement——把约定落成机制）

前述模块边界若只当「约定」，实现者「看似照做、实际双真相」就破 P1/P3/P5/P6/I6。本节把四处命根落成**可验证机制**（CI 可测）。

**(1) WriteDaemon——唯一写库的串行化协议（护 P1/P6）。** 全库写**只有一条路**：各模块（Gate / StateStore / interaction daemon / importer register·select·license）**不得自开 sqlite 写连接**，只能向 `WriteDaemon` 单线程队列提交 `WriteCommand{kind, payload, idempotency_key, txn_scope}`；daemon 持**唯一** connection、单线程、单事务提交。

| WriteCommand.kind | 调用方 | 事务边界 | 幂等键 |
|---|---|---|---|
| `gate_commit:<gate_fn>` | Gate | 单阶段单目标 | `(cycle,stage,target,artifact_hash)` |
| `state:<fn>` | StateStore | 单步状态迁移 | `(cycle,fn,args_hash)` |
| `interaction_in` / `interaction_reply` | interaction daemon | 短 | `(connector,idempotency_key)` / `(message_id,reply_hash)` |
| `interaction_request_create` / `interaction_request_resolve` | 编排器（sidecar 触发）/ interaction daemon | 短 | `(goal_id, request_hash)` / `(request_id, resolved_message_id)`；create 拒绝判据：`enabled=false`、items 超 `max_items_per_request`、同 goal 请求数（pending+resolved）≥ `max_requests_per_goal`（附录 C，《第一部分》§4.6.8） |
| `interaction_directive_confirm` | interaction daemon | 短 | `(directive_id, confirm_message_id)`；置 `directive.payload_json.confirmed=true`（《第一部分》§4.6.2 确认流水；directive 行非 append-only，DDL 兼容） |
| `import_register/select/license` | importer | 短 | `(candidate_id\|action, args_hash)`；**import deferred（M1–M3）的业务三写入（`external_import(selected_for_materialization)` + 占位 `baseline(planned)` + `question_dep(pending)`）不走独立 import 命令、亦非新增 WriteCommand kind——归入 plan 阶段 `commit_phase(stage='plan')` 的同一 phase_commit 事务（既有 `gate_commit:<gate_fn>` 命令族；同一事务并含 set_route(dependency_wait)、Qn 释放回 open、mark_cycle_done）**（《第一部分》§4.2.5，防半写）；其业务门禁含「占位 baseline 非 planned / provenance≠'external_import' / license_status≠'allow' → 拒」 |

**铁律**：长操作（runner 调用、训练、import clone）**绝不持写事务**——在事务外执行、完成后才提交一个**短**写命令。事务必须短（防写队列被长任务堵死——这正是 §6.8 ACK 排队、interaction 入账延迟的根因）。

**(2) gate_input_* 强制隔离（机制非约定；护 v2.3 纪律①）。** ① Gate 进程只拿**受限只读连接** + SQLite **authorizer**，`deny` 一切对 `execution_log` / `execution_observation` / `interaction_message` / `interaction_classification` / `interaction_reply` / **`interaction_request`** / `external_candidate` / `external_import` / `license_review` 的 `SELECT`（门禁判据**禁读**日志 / 聊天 / 文件请求 / 外部检索 / 候选审计态；逐表列名，不靠前缀通配）；② 门禁判据只从 `gate_input_*` 视图取数，视图**依赖闭包经 CI 自动测试不含**上述禁表；③ gate 输入快照入账。三者缺一，纪律①即退回口号。**对照视图 `v_metric_result_trajectory`（join metric_result × execution_log，供人 / 审计 / 对照 + reasoning 可达）属人侧视图、不在 `gate_input_*` 集；其底表含 `execution_log`，authorizer 既有 deny 自动拒 gate 读它。**

**(3) 状态机 + route 全转移矩阵（护「selection 不写 route」+ 不死循环）。** `derive_next_route(next_intent, plan_outcome)` 穷举（reasoning 只产 selection、**从不写 route**）：

| next_intent | plan_outcome | → route |
|---|---|---|
| attack | 含 build/exec | `attack` |
| attack | 仅 eval | `eval_only` |
| attack | 空 + 无 blocked | `reuse_only` |
| attack | blocked（撞 baseline 占用） | `dependency_wait` |
| attack | **import deferred（需 M4 物化，M1–3）** | **`dependency_wait`**：plan 已落业务三写入（`external_import(selected_for_materialization)` + 占位 `baseline(planned)` + `question_dep(pending)`）并与 set_route、Qn 释放、mark_cycle_done 同一 phase_commit（《第一部分》§3.6.3/§4.2.5），本轮写 dep 后收尾；问题因 pending dep 不可调度（§4.2.1）、**不重复登记**；M4 物化注册 legal → dep 机械 satisfied → 回可调度集 |
| decompose | — | `decompose` |
| terminate | — | 停机（本轮 route 不改写） |

`import_pending_materialization` **不是新状态、不是 StateStore 私有标记**，只是「占位 baseline 的 `question_dep` 处于 pending」这一处境的描述名（《第一部分》§3.6.3）；解除 = M4 物化（`baseline→legal` 机械 satisfied）或人工改依赖 / prune（§4.2.4 `record_question_dep` blocked 语义）。

**(4) import / license 状态机（护 I6 不被异步 license 撬动）。** 选择与 license 解耦、各自冻结、可回放：
- **选择冻结**：一次 select 绑定 `(question goal_ver, action_cycle, candidate_set_hash, policy_hash, selection_key)`；candidate_set 按 `action_cycle` 上界冻结；select 可**重放**（同输入→同序）。
- **license 异步**：`license_review` append-only、可人工 / 后补。**物化选择不读「当前 license」**，只读一个**冻结 `license_decision_snapshot_hash`**（某 `action_cycle` 时点已落全部 license 裁定的规范哈希）。
- **状态机**：`selected`（按 selection_key 选中、license 未定）→ 在冻结 license 快照下 `selected_for_materialization`(allow) / `rejected_by_license`(deny→按 selection_key 取下一个，仍确定性) → `imported` / `materialize_failed`。**后到 license 裁定不改既有 `selected_for_materialization`**（它绑旧快照）；要用新裁定须新 `action_cycle` 重选（新快照、append 新事件、不改旧）。「同问题同输入同 license 快照→同 import」可回放。

**供应链闭包（补全 §6.9 物化 manifest，护 M4 可审计复现）**：除 revision / submodule SHAs / `patch_set_hash` / LFS·artifact hashes / dependency lock / build image·env hash / `harness_adapter_hash` 外，还须记：artifact 下载源 + 系统包源 + 容器 digest + 编译器版本 + patch apply 顺序 + 生成文件哈希 + 运行命令 + 环境变量白名单 + 网络隔离声明。
