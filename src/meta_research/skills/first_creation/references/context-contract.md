# Companion context and handoff

This contract governs creation understanding/reassessment, first-Question synthesis, everyday Companion work and interface-initiated writing. The supplied runtime binding, schema, tools and permissions remain authoritative. This document defines content and responsibility; it grants no tools or operational permission.

## Project folder and human interaction

One Quest has one persistent assistant project folder, like a Codex project directory. New conversations use that same folder. Prefer the existing harness for starting, continuing, resuming and compacting native conversations; do not build another assistant state machine, memory system or compulsory handoff workflow around these capabilities. The application retains the simple Quest-to-folder and current-thread association, supplies current instructions and tools, and performs its own existing research operations when the human clicks their formal controls.

The assistant primarily helps the human understand research, examine assets, discuss directions and prepare Question or guidance content. Asset discovery and reading cover all research assets the human may access, not only the selected Quest or Cycle. Research query tools, tool discovery and authorized assistant-side analysis are available for that purpose; content is read as needed rather than injected in full. Formal Question creation, guidance delivery and HumanRequest submission occur only through the human's explicit UI action. The assistant itself does not control the Cycle engine or acquire research-write authority from having broad query access.

The business user begins with the actual assistant task and scope, not a Cycle stage. Supplied paths identify the model-visible working directory and inputs. Shared navigation, material and human collaboration guidance are reachable at their exact versions within the protected environment; their applicable content stays inline until that reachability is established.

They are not a reason to preload every source, perform a full directory scan, recompute hashes, or replay unrelated conversations. Protected input paths, work directory and reader scope must agree with what the model can actually access. A host path is not an actionable protected path. ## Manual Question drafting window

`manual_question_creation` identifies a window-scoped drafting task distinct from everyday conversation. Its input directly supplies the confirmed Seed, current six-field Proposal/draft and revision/hash, human words, creation context identity/generation and response schema. Preserve the confirmed Seed exactly and suggest changes only to the six Proposal fields for the human to edit and confirm. This reply does not confirm the Proposal, create a Question, or issue an Owner receipt. Use the supplied drafting response schema; the conversation `agent_proposal`/soft-constraint flow does not apply to this window. The common four-core-plus-two-optional Question meaning remains unchanged.

## Continuation and a fresh native session

A phase change is not by itself a new root. Within one native root, a necessary business continuation supplies the new human words, task or affected work, material changes and feedback, with accurate current scope. The runtime continues to maintain applicable instructions, tools, permissions, schema and effective history. Ordinary tool results do not require an extra business user message. This contract does not promise the common developer message is transmitted only once.

On compression, interruption or unknown results, continue the original operation through the shared continuity contract and the supplied accurate records. Recover the material actually needed for the pending judgment; do not reinterpret an old operation through a latest draft or repeat an effect whose result is unknown. Current permission still governs execution.

`/new` starts a fresh native session in the same assistant project folder. It receives applicable instructions, current task and capabilities, plus the folder and available prior-conversation entrances. Files, drafts and earlier results persist; a new conversation does not automatically know their contents. Read earlier requirements and work relevant to the human's request. Neither importing the entire transcript, scanning every file, repeating hashes nor creating a new handoff document is required. Use normal native continuation/resume for an existing conversation and a new native thread for `/new`; the folder is independent of that choice. Research workspace lifetimes follow [materials and custody](../../references/materials-and-custody.md#交接与工作区收尾), separately from the persistent assistant folder.

Creation-to-Quest context, when explicitly supplied, is accurate earlier material to read for the current task. Source and integrity handling use the existing input/Owner contract; do not turn that historical implementation path into an extra assistant-managed hash gate or lifecycle on every new conversation. Unavailable material is reported truthfully rather than reconstructed from guesses.

## First-Question parent and child

The parent keeps the creation conversation and organizes a fresh short-lived drafter for the supplied synthesis task. Give the child the exact current draft, prepared-basis binding, sealed-context entrances, route, relevant conditions, permissions and output schema. Use the actual harness's supported delegation form; inherited context or an explicit task package must make these same facts available. A smaller spawn message may point to an exact inherited task only when that task is actually inherited. The child receives no larger permission scope than the parent.

The parent records the actual returned child identifier, waits for the child result and checks the supplied schema and preservation of the relevant intent and basis. The child returns `content` and the route-specific `revision`; it does not invent its session identifier, issue Owner receipts or confirm creation. For a direct route `revision` is null. A literature route returns the complete revision, including an honest unchanged/empty assessment when appropriate. The human receives an editable Question and confirms it through the formal creation flow. The parent remains the original root; the child's completion is not a new Cycle or formal acceptance.

This content handoff is distinct from independent review. Where a particular task needs independent review, the root chooses the task and necessary context, evaluates the feedback and revises within its continuing work. No universal review packet or fixed fork mode is introduced for all Companion subtasks.
