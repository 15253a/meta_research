# Source evidence

Use this reference before reading or copying registered materials, reporting coverage, applying a reassessment, or choosing exact content for custody. Read the relevant sections for the present action; the current operation supplies the actual tool schemas and authorization.

## Read witnesses, host-direct citations, and coverage

Registered server references are persistent read-only entrances, directly accessible on the host at `source.absolute_path` and also via MCP material tools. You may inspect them directly with host shell/Python tools (`ls`, `head`, `tail`, `wc`, `grep`, `python`, etc.) or call `research_workspace.materials.discover` and `research_workspace.materials.read` directly through `tools.call(operation_id=..., arguments=...)` without calling `tools.catalog.page` or `tools.contracts.read` first. `research_workspace.materials.read` accepts `reference_ref`, `path`, `observation_ref`, `offset`, and `max_bytes` (at most 65536 bytes) and returns an opaque `read_witness`.

A citation contains `witness_ref` and a concrete section, file, or line description in `location` (for example `README.md:1-40`). Both citation forms are valid:
- **MCP read witness**: an opaque `read_witness.witness_ref` returned by `research_workspace.materials.read` in this operation (or explicitly inherited).
- **Host-direct citation**: the registered `reference_ref` (or `host:<reference_ref>`, or the mounted host path inside that registered reference) when inspected directly on the host.
Never invent forged or unregistered `witness_ref` values.

Coverage includes every registered entrance. Its `material_key` is the exact `reference_ref`. Each coverage record contains `kind`, `read_ranges`, and `unread_description`. `read_ranges` contains valid MCP or host-direct citations matching `material_key`. Use `read` only for a `file` reference that was completely read (either via host-direct read or MCP byte ranges covering all bytes). A directory is `partial` or `unread`, because lightweight inspection does not read every child file. Use `partial` with the actual observed citations and describe the unread scope concisely. Use `unread` with no ranges and a truthful entrance description. Claims about content need observed sources. Composition, gaps, and unfinished questions can describe an entrance or a missing source without claiming its content. Conditions stay beside the claim they qualify.

## Reassessment and inherited evidence

A reassessment names the supplied exact `predecessor`. Its `decisions` covers every prior statement once. `retain` preserves the original text, kind, conditions and citations. `replace` names new `replacement_refs` in `additions`. `needs_recheck` and `out_of_scope` record `affected_scope` and `creation_limit`, either `required_first_question` or `future_research`. Each decision records `applicable_conditions` and an explanation. `additions` contains all six groups for new statements only, complete current coverage and genuinely new selections. Excluded statements remain readable in applicability and do not remain supported current claims.

Choose `inherited_evidence` for MCP read witnesses from the supplied `evidence_facts`. Host-direct citations (listed in `host_cited_references`) do not require `inherited_evidence` entries; when retaining statements grounded by host-direct citations on unchanged mounted references, preserve those host-direct citations in `additions.coverage[ref].read_ranges` (`partial` or `read`) rather than marking the reference `unread`. Each `witness_ref` appears at most once. Use eligible `live_source` for current reuse, with `selected_material_key=null`. The Owner rechecks its original observation and range bytes against current entrances. It retains its original `operation_ref`; this is no new read. Use `managed_history` only for historical support, naming the original witness and an exact `selected_material_key` also listed in `inherited_selection_keys`. Never emit both kinds for the same witness. Managed history cannot enter current coverage or prove a changed live file was read. A stale linked locator or unretained source cannot guarantee historical bytes remain available. An old basis hash still identifies that history.

Use `inherited_selection_keys` to reuse eligible exact selected versions independently of witness disposition. For an unchanged file in managed custody, inherit its eligible witness once as `live_source` and retain its selected version here. Managed custody does not require a second `managed_history` entry for that witness. Do not put those old selections into `additions.selection` for another intake. Only new selections use current OriginalFile or WorkFile selectors. State historical limits beside affected claims and preserve unread scope.

## Work copies and custody selection

`research_workspace.materials.copy` accepts `reference_ref`, `path`, `observation_ref`, `effect_id`, and optional `max_bytes`. It streams one observed file into independent writable work under `execution.work_directory` (its returned `working_path` is a real host path); omitting the budget copies its observed size. Alternatively, for temporary use-and-discard inspection scripts during creation, you may copy needed files into `execution.work_directory` directly on the host without modifying originals. Do not copy or ingest files into RM/RG just for lightweight initialization-understanding: leave `selection` empty (`[]`) by default unless the user explicitly asks to formally retain or ingest a specific file or artifact. After creation is accepted, user-provided external directories and files remain persistently accessible read-only throughout the Quest (in `Mounted server materials`, DeepFetch scope, and `research_workspace.materials.*`), subject to actual host availability. Formal custody remains a separate choice. A reference into a research Session's temporary workspace follows the [handoff lifetime](../../references/materials-and-custody.md#交接与工作区收尾); registration does not make that directory permanent.

A selection contains `source`, `custody`, and `reason`. An `OriginalFile` source contains `kind="original_file"`, `reference_ref`, `path`, and `observation_ref`. A `WorkFile` source contains `kind="work_file"`, `work_ref`, `path`, and `trial_ref`. Use the `work_ref` from the execution binding and a path relative to this operation's work directory. For a copied file, use the receipt's `work_file`. `trial_ref` is the copy `effect_key` or `null` for a new result. Choose `managed` or `linked_local` custody for each exact file. Select originals and results separately to retain both, or return an empty selection to retain neither.

Formal custody applies only to selected content. `managed` custody preserves the selected bytes. `linked_local` custody retains a readable locator for the exact version and reports later source drift. Selection does not issue an acceptance receipt or manufacture research execution. Original producers, external paths, and imported results remain external provenance. Unselected originals remain available through their references and can later report changed or unavailable bytes. Unselected work files do not enter formal automatic saving.
